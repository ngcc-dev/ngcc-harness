## Attacks considered

- hash-03-1: A backward tree reduces C-Hash-1024 second-preimage work below 1024 bits (Design, Probable)

## Remediation

- **hash-03-1.** Root cause: in a VIL round the 736-bit message block is XORed into the left half of the state before CTR-Func and into the right half after it. A forward probe is therefore a predecessor of a target state when only the left 736 output bits match, because a free block absorbs the other 736. The costed repair is the one that the C-Hash team proposed and `report.md` records: reserve zero bits in every 736-bit block, so that a predecessor must also match the reserved bits. No cheaper credible repair was identified. The 1,536-bit C-Engine fixes the state at 1,472 bits, so the number of message bits per call is the only quantity that can move without a new permutation. Scope: Sub-algorithm, specification and code. The padding and block rule (§1.2.2 and Algorithm 1 line 2) changes for C-Hash-1024, and with it the message-block entry of §1.4, the rate statement of §4.1 and the second-preimage argument of Appendix C.7.2; the team says its Appendix C proof missed this strategy. In the code, `pad_message` and the block loop change. Impact: with the team's 352 reserved bits a call absorbs 384 message bits in place of 736, so a long message needs 736/384 = 1.917 times the C-Engine calls per byte, +92% (count). This is the team's stated throughput loss of about 48% (384/736 = 0.522). The smallest byte-aligned reservation that keeps the finding's tree model at 2^1024 calls for every tree depth is 280 bits, which leaves 456 message bits per call: 736/456 = 1.614, +61% (estimate, no margin). Comparing the exponent alone, without the depth factor, gives 288 bits: 736/448 = 1.643, +64%. Both ends of the range are above 10%, so the answer does not depend on the margin. The lower end counts trees deeper than the report's two levels, which the team's reply describes and the report has not assessed: 64 reserved bits (+9.5%) hold the two-level tree at 2^1024, but a third level then costs 2^968, so that reservation blocks only the two-level form and is not costed. C-Hash-512, the LDRH path for messages under 1,472 bits, and the initialization and finalization calls are unchanged. Keeping 736 message bits per call would instead need a state of about 1,024 + 736 = 1,760 bits under the same model, and so a permutation wider than C-Engine; that is not costed. Not checked: the team's post was not re-read, and the figures are those recorded in `report.md`; where the reserved bits sit in the block; whether the revised mode meets the claims; the deeper-tree cost, which the report has not assessed.

## Evidence

- Baseline: Table 5 (physical p. 14) gives C-Hash-1024 `(b, w, n) = (1536, 64, 1472)`, `(z, h) = (1, 1472)`, CTR-Func. The message block is `n/2 = 736` bits (§1.2.2, physical p. 7). One 28-round C-Engine call absorbs one block (Algorithm 1 lines 3–6, physical p. 8; §4.1, physical p. 27). The claimed second-preimage level is 1024 bits (Table 6, physical p. 22).
- Source: `C Hash/Implementations/Reference_Implementation/CHash_1024/CryptHash_AlgorithmInstance.c:550–565` makes one `apply_P` call per 92-byte block; `:302–310` is CTR-Func with one `C_Engine1536_Perm28_plain` call (`:178–187`, 28 rounds); `:481–510` pads to a multiple of 736 bits. The code does the specified work.
- Model, from the finding: with a backward-step condition of `c` bits and `N` probes at each of `d` counters, a join with `N` forward states is expected when `N^(d+1) = 2^(d·c + 1472)`, so `log2 N = c + (1472 − c)/(d + 1)`. Control: `c = 736`, `d = 2` gives 981.33, the report's figure. The exponent falls towards `c` as `d` grows.
- With `z` reserved bits, `c = 736 + z`. `c ≥ 1024` needs `z ≥ 288`. At `z = 288`: 1173.3 for `d = 2`, limit 1024. At `z = 352` (the team's value): 1216 for `d = 2`, limit 1088. At `z = 64`: 1024 for `d = 2` and 968 for `d = 3`.
- Calls counted as the finding counts them, `d·N` backward probes and `f·N` forward calls for `f` prefix blocks (`4N = 2^983.33` at `z = 0`, `d = 2`, the report's figure): `python3 -B hash-03/fixing_cost_tree_model.py` prints the minimum over `d` as 2^1017.78 at `z = 272` (`d = 323`), 2^1025.76 at `z = 280` (`d = 317`), 2^1033.73 at `z = 288` and 2^1097.51 at `z = 352`. It prints the smallest byte-aligned `z` as 64 for two levels only, 288 for every depth by exponent alone, and 280 for every depth with calls counted.
- Calls per message byte are `736/(736 − z)`: 736/456 = 1.614 at `z = 280`, 736/448 = 1.643 at `z = 288` and 736/384 = 1.917 at `z = 352`; 736/672 = 1.095 at `z = 64`. Throughput is 456/736 = 0.620, 448/736 = 0.609 and 384/736 = 0.522 of the baseline.
- Message length: the VIL round index has 2^56 values (Table 1, physical p. 9). 2^56 blocks of 384 bits are 2^64.58 bits, of 448 bits 2^64.81 bits and of 456 bits 2^64.83 bits, all above the required 2^64 − 1 bits.
- Stated timings, as context only: C-Hash-1024 at 65,536 bytes takes 2,843.3 cycles/byte (REF) and 38.1 cycles/byte (OPT, AVX2) (Table 9, physical p. 30).
- Proposed fix: `report.md`, hash-03-1, "Proposed fixes", from the C-Hash team's reply of 2026-10-10: 352 zero bits in every 736-bit block, stated throughput cost about 48%. Quoted as reported by its source and not evaluated.
