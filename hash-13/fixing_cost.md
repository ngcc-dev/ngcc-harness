Impact: none
Scope: Function (small), specification and code
Assessed: 2026-11-24

## Attacks considered

- hash-13-1: Long messages reduce JuziHash-1024 second-preimage security below 1024 bits (Design, Confirmed)

## Remediation

- **hash-13-1.** The root cause is that a JuziHash-1024 block is XORed into the whole 1024-bit rate and every call of f_DM is the same function, so two states that agree on the 1024-bit capacity are merged by one corrective block wherever they stand in the message. A target of 2^k blocks then offers 2^k capacities, expandable messages can be built, a link costs 2^(1024 − k), and k reaches 54. The costed repair is the standard block counter of HAIFA (Biham and Dunkelman, ePrint 2007/278), carried in bits that hold no message: the index i of the block is XORed as a 64-bit value into a fixed 64-bit field of one capacity word, for example S2, of the permutation input, Y = P(S ⊕ In(M) ⊕ Ctr(i)). In(M) writes only S0, S1, S4 and S5 (§3.5), so the capacity words S2, S3, S6 and S7 carry 1024 non-message input bits and no message bit is displaced; BLAKE2 places its counter the same way, in state words that carry no message (RFC 7693, §3.2). The block size, the padding, In(M), the feed-forward and the digest stay as they are, and with i = 0 for the initialization call H(0) and Appendix B do not change. Under the finding's model the counter removes the position independence that the attack needs. Two branch states at different positions can still be merged, at the same birthday cost, by matching their capacities up to the difference of the two counters, but the merged state then continues at two different positions, and the next calls of the two branches differ in counter bits that no message block reaches. Branches of different lengths therefore no longer end in a common state, so the expandable message fails, and a state reached after j blocks can join the target only at block j, so each link trial matches one target capacity and not one of 2^k. Scope: Function, specification and code: f_DM takes the block index (§3.5.2 and §4.3), and in the code `juzi_update_dm` and its three calls in `juzihash1024_ref`. JuziHash-512 needs no change. Impact: none. The counter adds one 64-bit XOR (8 byte XORs in the byte-oriented reference code) and one increment to each call, against at least 24 × 256 = 6,144 S-box evaluations per call: 9/6,144 = +0.15% even when each S-box evaluation counts as one operation (count). No call is added, so a one-block message changes by the same fraction. The specification states the long-message loss (§5.5) and proposes no change, and the report records no proposed fix. The alternative of a counter carried in message-rate bits, 55 to 64 bits reserved in every block, costs +5.7% to +6.7% per byte (estimate), still under 10%, and a field of a whole 256-bit word costs +33.3%; neither is needed, because the capacity bits are free. The counter width and position are costing aids, not a proposed design. Not checked: other long-message techniques, such as diamond-based second preimages, against the counter version; the AVX2 code. Nothing was implemented or measured.
