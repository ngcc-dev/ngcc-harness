No: giving CTL-512 a 64-byte key-generation seed and a 64-byte message, c2 and shared key changes no stated public key or ciphertext size, because the stated ciphertext already holds a 64-byte c2, and adds an estimated 1% or less to key generation.

Impact: key generation +0% to +1% at CTL-512 (judgment)
Scope: Function (small), specification and code
Assessed: 2026-11-24

## Attacks considered

- kem-12-1: The specified CTL-512 public-key space has at most 256 bits of support (Design, Confirmed)
- kem-12-2: CTL-512 returns only 384 shared-secret bits (Implementation, Confirmed)

## Remediation

- **kem-12-1.** Root cause: f and g are regenerated from one 32-byte seed (short private-key format, physical p. 32; `ctl.h:192`), and the generator that expands it keeps a 32-byte key (`inner.h:1538,1553`). The costed repair is the one the submitters propose: a 64-byte seed, an expander that keeps the full width, and the matching private-key encodings. It is the cheapest credible repair because the seed is secret and appears in no public object. Scope: Function, specification and code: the seed and generator-key lengths (`ctl.h:192`, `api.c:185`, `inner.h:1538–1556`, which documents a 48-byte limit on the seed) and the 32-byte seed of §3.5.4 (physical p. 32). The private-key encoding changes. Impact: none on the public key and the ciphertext. The private key grows by 32 bytes: short format 3,105 to 3,137 (+1.0%), long format 15,617 to 15,649 (+0.2%). This is recorded and does not decide the answer. Key generation: +0% to +1% (judgment). The generator is the contest's `pseudoXOF`, which the ruleset costs as an ideal replacement by calls and bytes. Its calls stay the same in number. Each refill of the generator (`inner.h:1561–1577`) absorbs a counter and the key, 40 bytes as submitted and 72 repaired, and returns 128 bytes; one sampling attempt for f and g draws 2n = 4,096 64-bit values (`keygen.c:11028–11030`), which is 256 refills. Its bytes grow from 43,008 to 51,200 (+19%); in blocks of b bytes, with the input absorbed once, from 512 to 768 at b = 64 (+50%) and not at all at b = 136. The four other calls that take the seed or key (`prng_init` twice, `prng_get_bytes` and `make_rr`: `inner.h:1547–1556,1582–1590`, `api.c:93–97,194–196`, `keygen.c:11868`) run once per attempt or once per key. The specification names the NTRU equation as the most time-consuming step of key generation (physical p. 32) and the dominant bottleneck (§7.1, physical p. 52). At about 2,000 word operations per 64-byte block, the 256 added blocks of one attempt are about 0.5 million operations, and the submitted benchmark (`ctl_kem_benchmark_raw.csv`, 100 runs) gives at least 780,531,423 cycles per CTL-512 key generation, so each sampling attempt adds roughly 0.07%; the change reaches 1% only past about 15 sampling attempts per key and 10% only past about 150. Every attempt also computes the deepest-level resultants of f and g before the solver (`keygen.c:11882`), and no rejection rate is stated, so the number of attempts per key was not determined; this is why the figure is a judgment. Alternative, not costed: in the helper as built, the 64-byte key takes two SM3 compressions per 32-byte output block where the 32-byte key takes one, so a sampling attempt takes 2,048 compressions instead of 1,024, roughly 0.27% of the minimum key generation per attempt by the same rough measure. The value rr is not widened. It is 32 bytes (`ctl.h:191`), derived from the seed (`api.c:91–97`), and feeds neither f, g nor h, so it does not cap the key-generation root that the finding concerns; with the repair it is derived from the 64-byte seed. It keys only the code's implicit-rejection output (`api.c:142–165,784`), while Algorithm 6 (physical p. 43) returns ⊥ when the re-encryption check fails and Theorem 2 (physical p. 48) is stated for that explicit-rejection KEM, so the specified security claim does not rest on rr. If a revision keeps implicit rejection and widens rr to 64 bytes, the long private key grows by 32 more bytes (+0.2%), the short format, which regenerates rr, does not change, and the rejection hash that decapsulation always computes absorbs 32 more bytes of about 4,200 (as built 132 → 134 SM3 compressions), which is none against the stated decapsulation time.
- **kem-12-2.** Root cause: the code sets the message, c2 and the shared key to 48 bytes (`api_3329_2048.c:5`, `ctl.h:249`, `KEM_AlgorithmInstance.c:21,68,75,84,116`). §3.5.3 (physical p. 31) assigns 64 bytes to c2 at CTL-512, and the specification does not state the key length. The costed repair uses 64 bytes for all three, which is the direction of the submitters' response. The plaintext space allows it without new parameters: s is an n = 2048-bit value derived from m, and m is recovered as c2 ⊕ Hash_m(s) (Algorithm 3, physical p. 40; `api.c:677–708`), so only the length of c2 limits m. The failure probability concerns the decoding of c1 and is not touched. Scope: Single line, specification and code: one length, written in seven places in the code, and the key length that the specification leaves out. The ciphertext encoding changes in the code. Impact: none against the stated sizes. Table 3 states 2,305 bytes, which by the specification's own encoding rules is one header byte, c1 at 35 bits per four coefficients (2,240 bytes) and a 64-byte c2. The stated size therefore already contains the 64-byte c2, and the repair adds no byte to it. The built library differs from the stated size for another reason: it returns 2,353 = 1 + 2,304 + 48, because it packs c1 at 36 bits per four coefficients (`kem3329.c:1231`). With the repair it returns 2,369, which is 16 bytes (+0.7%) more than it does now. It is 48 bytes above Table 3 before the repair and 64 bytes (+2.8%) after, and all 64 come from the packing of c1, which the finding does not concern; with c1 packed as specified the repaired size is the stated 2,305. Encapsulation and decapsulation: none. The hash calls are the same in number, and in the contest helper as built they also take the same number of SM3 compressions.
