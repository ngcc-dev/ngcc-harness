## Attacks considered

- kem-27-1: NTRE-512's 256-bit secret seed caps offline key-recovery work (Implementation, Confirmed)

## Remediation

- **kem-27-1.** Root cause: `NTRE_SYMBYTES` is 32 (`src/params.h:10` in the reference trees, `params.h:10` in the optimized trees), so key generation draws a 32-byte seed for each of f' and g' (`KEM_AlgorithmInstance.c:91–105`), while Algorithm 5 (physical p. 6) draws s from B^64. The costed repair is the one the NTRE team proposes: set `NTRE_SYMBYTES` to 64, so that the code follows the specification. Every use of the seed length goes through that macro (`KEM_AlgorithmInstance.c:26–104`, `src/symmetric.c:36–41`), so nothing else changes. Scope: Single line, code; one constant in each of the six `params.h` copies. The specification stays as it is. Impact: key generation +0% to +1% at NTRE-512 (estimate). The seed is used only inside key generation. It is not stored in the public key, the ciphertext or the secret key, so no object changes size. Key generation makes the same two XOF calls with the same 576 output bytes each, and each call absorbs 65 bytes instead of 33; the generator returns 64 bytes per seed instead of 32. Encapsulation and decapsulation do not use the seed. The XOF is the contest's `pseudoXOF` and the generator the contest DRBG, which the ruleset costs as ideal replacements by calls and bytes. Counted that way, with the input absorbed once and output in blocks of b bytes, the two XOF calls take 18 → 20 blocks at b = 64 and 10 → 10 at b = 136, and the generator output stays one block. Against the dominant work of one key generation, which is two NTTs of 2,304 coefficients, the blockwise inversion of f, one blockwise product, G(pk) and the sampling, that is +0.6% at b = 64 and +0.0% at b = 136, and +1.0% if the arithmetic weighs half as much as counted. The proposal states no sizes or timings. Alternative, not costed: the helper as built hashes the whole input with a 4-byte counter for every 32-byte output block (`auxfunc.c:482`), so the longer input needs two SM3 compressions per block where the submitted one needs one, and the DRBG one more compression per seed. Key generation then takes 135 compressions instead of 97, which by the same operation count is +11% of key generation (+6% to +17% with the arithmetic weighted double or half). That figure is a property of the placeholder's counter mode, which the ruleset does not cost. Not checked: a measured profile, and the optimized trees.

## Evidence

- Baseline sizes: Table 4 (physical p. 38) and Algorithms 8 and 11 (physical pp. 7–8). NTRE-3457-2304: pk = ct = 12 · 2304 / 8 = 3,456 bytes; sk = 2 · 3,456 + 32 = 6,944 bytes. None of the three contains the sampling seed.
- Sampling: Algorithm 5 outputs XOF(s, n/4), which is 576 bytes at n = 2304 (`NTRE_SAMPLEBYTES`, `src/params.h:19`). Key generation calls it once per attempt for f' and once for g' (Algorithm 8, physical p. 7).
- Helper count, as built: output blocks per sampling call = 576 / 32 = 18. SM3 compressions per block = ceil((L + 9) / 64), where L = 1 + seed + 4 is the prefix, seed and counter: 1 at L = 37 and 2 at L = 69. Two calls: 36 submitted, 72 repaired. G(pk) = ceil((3,456 + 9) / 64) = 55 in both. Totals: 36 + 55 = 91 and 72 + 55 = 127. The DRBG (`drng.c:265–310`) adds per seed one compression of V per 32 output bytes and two for the update: 3 per 32-byte seed and 4 per 64-byte seed, 6 and 8 for the two seeds.
- Count: `python3 -B kem-27/fixing_cost_keygen_work.py`. It counts 32-bit word operations: 2,080 per SM3 compression (GB/T 32905 §5.3); one NTT 144,000 (`src/ntt.c:167–209`: one radix-2 layer, two radix-3 layers, five radix-2 layers, with fqmul as one product and a 4-operation Montgomery reduction and Barrett reductions of 5); inversion of f 136,512 (`src/ntt.c:255–282`, 576 blocks with a 27-product Fermat inversion each); one blockwise product 45,504; sampling and packing 27,648. Arithmetic in all 497,664 with two NTTs. It prints: as built 97 → 135 compressions with the DRBG, hash share 28%, key generation +11.3% (+17.1% and +6.3% with the arithmetic weighted half and double); idealized at b = 64 XOF blocks 18 → 20, key generation +0.6% (+1.0% at half weight); at b = 136, 10 → 10 and +0.0%. One attempt at f is counted. A retry after a non-invertible block (`poly.c:92–118`) repeats the sampling call, the NTT and the inversion together, so it changes the shares little; the retry rate was not computed.
- Stated timings (Table 4, physical p. 38), context only: NTRE-3457-2304 key generation 376,672 cycles in C and 137,912 with AVX2. The table does not separate hashing.
- Proposed fix, quoted as reported and not evaluated: the [NTRE team's response](https://list.niccs.org.cn/archives/list/pkcforum@list.niccs.org.cn/message/OAGYDCAYEJTJ6WE5PHBNNCTAGDZ57LXD/) sets `NTRE_SYMBYTES` to 64 and regenerates the KATs.
