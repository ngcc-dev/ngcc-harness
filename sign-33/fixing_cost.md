## Attacks considered

- sign-33-1: Publicly reproducible signing keys (Implementation, Confirmed)
- sign-33-2: A 256-bit implementation prehash limits forgery security to 128 bits (Implementation, Confirmed)
- sign-33-6: Restricted oil terms enable a public-key-only VDOO forgery (Implementation, Confirmed)
- sign-33-7: Moving the message/signature boundary forges new messages (Implementation, Confirmed)
- sign-33-9: A wedge-intersection attack on VDOO-512 is estimated at 2^379 gates (Design, Lead)

## Remediation

- **sign-33-1.** Root cause: `get_randombytes` draws from a file-local `DRNG_ctx drng` that the wrapper never seeds (`rng.c:4,11-14`), and the API generator `drng_algorithm` is declared and never read (`SIG_AlgorithmInstance.c:8`). The costed repair is the usual one for a missing seed: `get_randombytes` reads the API generator. The specification already says that all randomness comes from the ICCS DRNG initialized from a seed (§7.2, physical p. 21; §7.6, physical p. 23), so it stays as it is. Scope: Single line, code (`rng.c:13`, the same file in all six trees). Impact: none. The code did not skip specified work: `SM3_DRNG_Generate` has no check of its state and does the same hashing on a zeroed context (`drng.c:265-315`), and the number of calls does not change. The same line also feeds signing (sign-33-4, High, not costed). The report records no proposed fix.
- **sign-33-2.** Root cause: the wrappers reduce every message to `HASH_LEN = 32` bytes before signing and verifying (`vdoo_config.h:81`; `api.c:24-25,45-46`), at all three levels. Algorithms 4 and 5 write d = H(H(msg) || salt) with H: {0,1}* → F_q^m and give no length for the inner hash (physical pp. 9–10; §7.4, physical p. 22). The costed repair is the usual one for a narrow prehash: an inner digest of twice the level, 64 bytes at VDOO-256 and 128 bytes at VDOO-512, stated in the specification and set in the code. Scope: Function, specification and code; the code change is the constant and the buffers sized by it (`api.c:24,45`, `vdoo_sign.c:266`, `vdoo_verif.c:86`). Impact: none. The digest is only hashed: the signature is (s, salt) and holds no copy of it, and the target space F_q^m has 760 and 1560 bits, so nothing transmitted grows. The message is absorbed once as before, and each target derivation hashes 80 or 144 bytes where it hashed 48, against 4,289,250 and 20,229,300 public coefficients read per verification. The 16-byte salt is the subject of sign-33-3 (High, Proof gap) and is not costed. The report records no proposed fix. Not checked: the contest XOF is taken as an ideal replacement of the needed width, and a wider hash may cost more per message byte; this is not counted.
- **sign-33-6.** Root cause: `is_allowed_oil1` and `is_allowed_oil2` keep a vinegar–oil product only when the oil variable has the index of the equation (`vdoo_keypair.c:203-205,219-221`), where §4.3 (physical p. 7) gives every equation of an oil layer the products with all oil variables of that layer. The costed repair makes the two predicates follow the specification. Scope: Function, code (six `vdoo_keypair.c` files; the specification is sound). Impact: none. No size changes: the public key is the dense m·n(n+1)/2 coefficients either way, and the secret key already stores F in that dense layout (`vdoo_keypair.h:22`). Key generation and verification do the same work: `generate_public_key` multiplies full matrices with no test on coefficient values (`vdoo_keypair.c:296-355`, `parallel_matrix_op.c:54-69,154-165`). Signing is where the code skipped specified work: the signer multiplies only nonzero coefficients (`vdoo_sign.c:86,102`), so the dense layers add vinegar–oil products, 51,700 → 8,602,000 per attempt at VDOO-512, and an attempt in which nothing fails reads the same coefficients and does ×1.27, ×1.22 and ×1.47 the multiplications at the three levels. The submitted filter also makes each layer's matrix diagonal, so an attempt succeeds only if every one of the o1 + o2 diagonal entries is nonzero, probability (1 − 1/q)^(o1+o2) = 0.031, 0.72 and 0.48 before the diagonal layer is counted. With dense layers the expected attempts fall from 85.7 to 3.7, from 1.45 to 1.05 and from 2.14 to 1.05, and the expected work per signature is 0.07 to 0.08 (VDOO-128), 0.77 to 0.93 (VDOO-256) and 0.51 to 0.77 (VDOO-512) of the submitted work, counted in coefficient reads and in multiplications. The answer uses expected iterations, as the ruleset prescribes for a rejection loop. What would tip it is the cost of a signature that succeeds at its first attempt, which is the common case at VDOO-256 before and after the repair (probability 0.69 and 0.95): by that measure VDOO-256 signing is between unchanged (reads) and +22% (multiplications). Not checked: nothing was run, so the attempt counts are the model's and not measured; the optimized trees share `vdoo_sign.c` and the predicates, and their vector routines were not read line by line.
- **sign-33-7.** Root cause: `sig_verify` ignores `sn_len_bytes`, concatenates `m || sn` and lets `crypto_sign_open` take the last `CRYPTO_BYTES` as the signature (`SIG_AlgorithmInstance.c:61-83`, `api.c:36-48`). The costed repair is the report's: reject `sn_len_bytes != CRYPTO_BYTES` and verify the caller's message and signature separately. Algorithm 5 (physical p. 10) already takes a message and a fixed-format σ = (s, salt), so the specification stays. Scope: Function, code. Impact: none; one comparison is added and the work of `vdoo_verify` is unchanged.
- **sign-33-9.** Lead; it does not decide the answer. Root cause: the last oil layer is large for n. VDOO-512 has n = 455 < 3·o2 = 525, where §5.5 (physical p. 18) describes VDOO as having n ≥ 3·o2 and the other two sets do (137 ≥ 120, 300 ≥ 204). The repair is a new VDOO-512 parameter set. Scope: Parameter set, specification and code. With the finding's own model and no margin, the estimate reaches 2^512 once v + d + o1 ≥ 314 at m = 195, that is 34 variables more outside the last oil layer than submitted. The two ends of that choice are: (a) move 34 variables from the second oil layer to the first, (v, d, o1, o2) = (260, 10, 44, 141), which leaves n and m and so every size, key generation and verification unchanged, with expected signing work still below the submitted baseline; (b) keep the layers and add 34 vinegar variables, (294, 10, 10, 175), which gives public key +15.5%, signature +7.2%, verification +15.5% and key generation +23%. End (a) is not shown to be admissible: the specification's rectangular MinRank estimate has target rank o2 (physical p. 17), VDOO-512 has the highest o2/m of the three sets (175/195 against 40/70 and 68/95), and that estimate could not be recomputed at o2 = 141 because the specification does not state the rule for its operating degree b. The With leads answer is therefore by judgment for the middle of the range, where 17 added vinegar variables give public key +7.6% and key generation +11%. It would be No, with no impact, if the rebalanced set (a) keeps the specification's own estimates at 2^512. The estimates are lower bounds without margin. Not checked: ePrint 2026/2528 was not read, and the mapping of parameters to the intersection instance is inferred from the report's figures and §5.5; the semi-regularity and generic-rank heuristics; any attack other than the wedge estimate at the changed parameters.
