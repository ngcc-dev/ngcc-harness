No: replacing the multi-pipe SM3 hash, the SM3 counter-mode XOF and the SM3 Hash-DRBG of QingLuan-384 and QingLuan-512 with primitives whose internal state is as wide as the level changes no transmitted object and, costed by dimensions, adds no hashing work.

Impact: none
Scope: Sub-algorithm (large), specification and code
Assessed: 2026-11-23

## Attacks considered

- sign-20-3: Nested SM3 multicollisions give sub-target message binding for QingLuan-384 and -512 (Design, Confirmed)
- sign-20-5: Qing Luan's random-generation state caps the 384- and 512-bit sets at 256 bits (Design, Confirmed)

## Remediation

- **sign-20-3.** The root cause is that every pipe of `Hash` is an iterated SM3 with a 256-bit chaining value, so the concatenation is inverted in about 2^256 times a polynomial in the pipe count. More pipes or a longer output do not change that. The costed repair replaces `Hash` at the 384- and 512-bit sets with a hash whose chaining state, or sponge capacity, is wide enough for the level. This is the usual repair for a hash narrower than the level; the report records no proposed fix. Scope: Sub-algorithm, specification and code (§1.5.2, `src/hash.c` and its `api_pkc/hash_adapter.c` copy in both sets). Impact: none (judgment). No transmitted object changes, because digests and the salt are already 2λ bits and round seeds λ bits. The submission names no wider hash, so the speed is costed by dimensions. The submitted hash already carries 768 and 1,024 bits of chaining state and pays for them: it runs 3 and 4 SM3 compression calls for every 64-byte block, which is 21.3 and 16 message bytes per call. A replacement with the same block and state dimensions absorbs the same bytes per step, so the dimensions add no work. The cost of one step of a real wide primitive against 3 or 4 SM3 calls was not determined; the answer would change if the replacement hash and XOF made a signature at least 10% slower than the submitted ones, which do most of the symmetric work (see Evidence). The submission's property of being built on SM3 alone cannot be kept at these two levels by a standard technique. A new wide-state mode of SM3 would be a new construction and is not costed. QingLuan-384 is the optional level and could be withdrawn instead; QingLuan-512 is required.
- **sign-20-5.** Three states are narrower than the level. (a) The Hash-DRBG seed is fixed at 32 bytes (§1.5.4, physical p. 5; `src/utils.c:28,45–46`). The repair widens the DRBG seed and state to the level, which needs the wider hash of sign-20-3 underneath. The values are secret, and the DRBG supplies only 144 or 192 bytes per signature (`src/sign.c:70–71`). (b) The QingLuan-512 XOF squeezes `SM3(K || BE32(i))` with a block-aligned 128-byte `K`, so one 256-bit chaining value fixes every output block (`src/hash.c:361–367`). (c) The per-signature round seeds come from the same XOF (`src/sign.c:73–82`). The repair for (b) and (c) rebuilds the XOF so that the state carried between output blocks is at least as wide as the level. With `Hash` replaced under sign-20-3 this is the same change of primitive and is counted once. Scope: Sub-algorithm, specification and code. Impact: none (judgment). `Seed_pk` (2λ bits) and the opened round seeds (λ bits) keep their lengths, and nothing else that is sent depends on these states. The submitted squeeze already costs 2 SM3 compression calls per 32 output bytes at 384 and 3 at 512, so a replacement of the needed state width is not costed as slower. The report records no proposed fix. The report says the block-alignment argument does not reach the 96-byte QingLuan-384 key; the XOF is costed as replaced at both levels, because sign-20-3 replaces the hash that keys it.

## Evidence

- Baseline sizes, §1.12 (physical pp. 9–10): |pk| = 227 and 302 bytes, |sig| = 164,940 and 292,816 bytes at 384 and 512. Control with the §1.12 formula and the parameter table on p. 9 (t, w, n = 763, 631, 370 and 1018, 842, 491; Seed 48 and 64, Salt and Hash 96 and 128 bytes): 96 + 2·96 + 631·48 + 631·96 + 132·(324 + 139 + 96) = 164,940 and 128 + 2·128 + 842·64 + 842·128 + 176·(430 + 185 + 128) = 292,816. No term changes, because no length changes.
- Hash work: each pipe compresses every block (`src/hash.c:193–205`), and `HASH_PIPES` is 3 and 4 (p. 9), so 64/3 = 21.3 and 64/4 = 16 bytes are absorbed per SM3 compression call.
- XOF work: each 32-byte output block is `sm3()` over `PARAM_HASH_BYTES + 4` = 100 or 132 bytes (`src/hash.c:361–367`); with at least 9 bytes of SM3 padding that is 2 or 3 compression calls.
- Share of the symmetric work at 512 (count, expected): a round expansion draws n·8/7 + n·128/127 = 1,056 bytes (`src/rsdp.c:48–76`, one byte per draw; `src/mpc.c:62–63`), which is 33 output blocks or 99 compression calls, after 16 calls to absorb 196 bytes. It runs twice per round (`src/sign.c:91,112`). `cmt0` hashes 491 bytes (32 calls) and `cmt1` 196 bytes (16 calls). That is 278 calls per round and about 283,000 for t = 1018 rounds, plus about 55,000 for the transcript digests, the matrix and the seed leaves. §4.1.2 (p. 19) gives 98.97 million field multiplications for the same signature and §4.2.2 (p. 21) about 0.87 s; the specification gives no breakdown.
- DRBG: 48 + 96 = 144 and 64 + 128 = 192 bytes per signature against the counts above, which is under 1%.
- Nothing was measured, and the report's witnesses were not re-run. The files cited are under `Implementations and Test_Vectors/Implementations/Reference_Implementation/QingLuan-512/`; the QingLuan-384 copies of `hash.c`, `utils.c`, `sign.c`, `mpc.c` and `rsdp.c` are byte-identical.
