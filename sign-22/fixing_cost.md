## Remediation

- **sign-22-1.** Make `mu` twice the level, 96 bytes at 384 and 128 bytes at 512, and state the output length of `H_gen`, which Algorithms 6 and 7 leave open (physical pp. 33–34). `mu` is only hashed, into the signing seed and the challenge (`sign.c:317–321,369–373,521–525`), and is not sent. Rhyme-SM3 calls the contest's KDF-SM3 (`rhyme_xof.c:1–4`), so calls and bytes are counted for an ideal XOF: one call squeezes 32 or 64 more bytes. Scope in that profile: Single line, specification and code (`CRHBYTES`, `params.h:11`). Impact: none. Rhyme-SHAKE needs more, because SHAKE256 has a 512-bit capacity and a longer `mu` leaves its generic collision near 2^256. There `mu` needs a sponge of capacity 768 or 1024 bits, which at the same permutation has a rate of 104 or 72 bytes against 136. Scope, and the scope of the finding: Sub-algorithm, specification and code, since the specification names SHAKE256 (physical p. 33). Impact: verification +2% at Rhyme-SHAKE-384 and +7% to +9% at Rhyme-SHAKE-512 (estimate), because `mu` absorbs the whole public key; signing gains about 1% of its Keccak permutations. Only the `mu` call is widened. The other SHAKE256 calls of these two sets are not the subject of a finding and were not costed. Withdrawing the two SHAKE sets is an alternative. Not counted: for a long message the hashing of `M` dominates signing and verification, and in the Rhyme-SHAKE profile its cost per byte rises by 136/104 or 136/72.
- **sign-22-2.** Assign `rho_0` at least the level, which Algorithm 5 leaves open (physical p. 31), and widen the root, `seed_sk` and `K` from 32 bytes to 48 or 64 (`params.h:10`, `sign.c:240–249`, `keygen/kg_main.c:59–72`). All three are secret. `seed_A` stays 32 bytes, which the Table 3 public-key sizes assume. Scope: Function, specification and code. Impact: none on transmitted objects; the secret key grows by the 16 or 32 bytes of `K` (45,760 and 44,864 bytes in Table 3).
- **sign-22-4.** The costed repair is the proposal recorded in the report, quoted as recorded and not evaluated: replace the closed-form boundary expression for `M` (physical p. 64) by the cumulative-ratio maximum of physical p. 63 or a proved upper bound, and fix the enumeration order and the Gaussian convention of Algorithm 3. Scope: Function, specification (the constant and the loop order of Algorithm 3, with Appendix A). The algorithms and the parameter table stay. The submitted sources already contain this repair: `v` is enumerated in ascending order, and `M` is 1.002215, 1.001130, 1.001124 and 1.000567 (`RHYME_M_Q60`, `rhyme_v_0` and `rhyme_v_1` in the SHAKE trees' `params_tables.h`, lines 27, 152 and 165 at 128), each above the required maximum. Impact: none. The code does not change, and Table 3's acceptance rate of 0.5 for `z1` and its repetition counts are those of the source constants (0.50 to 0.51 by the script), so the baseline already includes a constant that meets the condition of p. 63. Signature sizes do not depend on `M`.
- **sign-22-6.** Make the Rhyme-SM3 XOF absorb input of any length. It buffers at most 8,192 bytes and returns zeros after an overflow (`sm3_xof.h:16`, `sm3_xof.c:40–50,118`). Scope: Function, code. Impact: none for the lengths the submitted code hashes, |pk| + |M| up to 8,192 bytes. Above that the submitted code computes no representative, so there is no baseline to compare with. Rejecting long messages is not costed as a repair, because the call requires messages of up to 2^63 bits.
- **sign-22-8.** Set the Rhyme-SM3 challenge weights to the 30, 58, 113 and 115 of Table 3, in place of 23, 44, 77 and 87 (`params_tables.h:18,177,386,600` in the SM3 trees). The specification is sound and stays. Scope: Single line, code (one constant per set). Impact: none. The sizes are stated for the Table 3 weights, the challenge sampler needs the same expected number of XOF blocks, and the work of no other step depends on `tau`. The other rows of the SM3 trees' table (bounds and widths) also predate Table 3 and are not part of this finding; taking the whole Table 3 table gives the same expected repetitions (ratio 0.995 to 1.000 by the script).
