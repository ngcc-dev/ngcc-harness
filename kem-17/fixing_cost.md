No: drawing the random values from the API generator, widening the HEP-QC-7 secret seeds and shared key to 64 bytes, and giving the wrapper XOF a state as wide as the level change no transmitted object and add no counted work.

Impact: none
Scope: Function (small), specification and code
Assessed: 2026-11-23

## Attacks considered

- kem-17-1: Publicly reproducible secret keys (Implementation, Confirmed)
- kem-17-2: HEP-QC-7 has at most 256 bits of key-generation support (Design, Confirmed)
- kem-17-3: First encapsulation in each process is publicly reproducible (Implementation, Confirmed)
- kem-17-6: Every seed expansion passes through a 208-bit XOF state (Implementation, Confirmed)

## Remediation

- **kem-17-1, kem-17-3.** One change repairs both: `prng_get_bytes` (`common/symmetric.c:32–34`) draws from the API generator, the call that the comment at `ref/KEM_HEP_QC.c:33–34` shows, and no longer from the file-scope context that nothing seeds. `seed_KEM`, `m` and `salt` (`ref/KEM_HEP_QC.c:72,125,126`) then come from the seeded generator on every call. In both findings the report asks that the entropy come from the API generator. The change also takes the wrapper's generator, whose output and next state share a prefix, out of the path of `m` and `salt`, which is the consecutive-ciphertext route of kem-17-3. Scope: Function, code. Algorithm 4 line 1 and Algorithm 5 lines 1–2 (physical pp. 16–17) already require fresh random values. Impact: none. Three generator calls replace three generator calls, and no object changes. If the wrapper's generator is kept and seeded, its output call and its state update also need separate inputs; that variant was not costed.
- **kem-17-2.** At HEP-QC-7, set the secret seeds (`seed_KEM`, `seed_PKE`, `seed_PKE.sk`, `θ`) and the shared key `K` to 64 bytes; §4.2 fixes 32 bytes for every set. The message is already 512 bits at HEP-QC-7 (`k` = 512, Table 4.1), so the plaintext can carry a 512-bit key and no parameter moves. `G` then outputs 1,024 bits and the seed-splitting hash 768 or 1,024, lengths that the hash of §3.1 supports (physical p. 10). `J` must output 512 bits; `hash_j` is built from three SM3-256 calls (`common/symmetric.c:86,93,98`). Scope: Function, specification and code (§4.2, `SEED_BYTES` and `CRYPTO_BYTES` for hep-qc-7, `hash_j`). Impact: none. The ciphertext carries no seed. The public key carries only the public seed, which can stay at 32 bytes; if the single `|seed|` is widened instead, the public key grows by 32 bytes (+0.00025%). The decapsulation key grows by 64 bytes. The added hash output is a few SM3 calls against 201,148 compressions per encapsulation. Not checked: whether the 256-bit `H(ek)` or the 16-byte salt limit the 512-bit set; the report records no finding on them.
- **kem-17-6.** Give the wrapper XOF a state as wide as the level. `CTX_LEN * 8` is passed as a bit length at `common/symmetric.c:24,43,115`, so 26 bytes of the 208-byte context are written. The cheapest repair sets the state and the hashed buffer to the level, 32 bytes at HEP-QC-5 and 64 bytes at HEP-QC-7, with the lengths in one unit. The hashed buffer is declared with `CTX_LEN * 8` bytes (`:112`), so it follows `CTX_LEN`. Scope: Function, code (`CTX_LEN` and the three length arguments). The specification uses an abstract XOF and does not describe the wrapper's state. Impact: none. The submitted wrapper hashes the 208-byte buffer, 182 bytes of it zero, once for every 32 output bytes. With a level-wide buffer the count of SM3 compressions falls: to 0.25 and 0.29 of the submitted count in key generation and decapsulation at HEP-QC-5, and to 0.75 and 0.78 at HEP-QC-7. Alternative: the unit fix alone, which writes all 208 bytes, makes every state update 7 hash calls where it is 1. SM3 compressions then rise by a factor 3.99 and 3.82 in key generation and decapsulation at HEP-QC-5, and 3.98 and 3.65 at HEP-QC-7; encapsulation changes by under 1%. A 64-byte state inside the unchanged 208-byte buffer gives a factor 1.50 and 1.44 at HEP-QC-7. The share of SM3 work in each operation was not measured, so these are not timing predictions. The answer depends on the state width: it is No for a state and buffer at the level, and with the 208-byte state an operation is at least 10% slower as soon as SM3 work is more than about 4% of it. HEP-QC-1 and -3 need no change.

## Evidence

- Baseline: Table 4.1 and Table 4.2 (physical p. 18), with `|ek| = |seed| + ⌈n/8⌉ + 8k·⌈n/64⌉`, `|dk| = |ek| + |seed| + ⌈k/8⌉ + |seed|` and `|c| = ⌈n/8⌉ + ⌈n1·n2/8⌉ + |salt|`. The script reproduces all four rows; HEP-QC-7 is 12,644,449, 12,644,577 and 49,297 bytes.
- Command: `python3 -B kem-17/fixing_cost_xof_work.py`. With 64-byte secret seeds HEP-QC-7 gives 12,644,449, 12,644,641 and 49,297 bytes; with every seed at 64 bytes, 12,644,481, 12,644,673 and 49,297.
- Hash work: `pseudoXOF` makes one SM3 call over the input and a 4-byte counter for every 32 output bytes (`Lib/auxfunc/auxfunc.c:500–521`). SM3 pads `B` bytes to `⌈(8B + 65)/512⌉` blocks: 4 for the 208-byte buffer with its counter, 2 for 64 bytes, 1 for 32 bytes. `xof_proc` makes one output call and one state call (`common/symmetric.c:111–116`). A 4-byte request costs 4 + 4 compressions as submitted, 1 + 1 and 2 + 4 with a level-wide buffer, and 4 + 28 with the 208-byte state. In calls and bytes: every variant makes two `pseudoXOF` calls per request; the level-wide buffer lowers the bytes hashed per call from 208 to 32 or 64, and the 208-byte state raises the bytes produced per request by 182.
- Call sites: 3 bytes per sampled index (`common/vector.c:69`), `k/8` bytes per matrix row (`:349`), 4 bytes per permutation index (`:421`), `4·ω_r` bytes per encryption vector (`:104`), `⌈n/8⌉` bytes for `h` (`:206`), the matrix tail (`common/code.c:138`). Decapsulation regenerates `y`, `x`, `T` and `P` (`common/parsing.c:27–31`); the permutation has 197,184 entries at HEP-QC-7.
- Script output, submitted code: key generation, encapsulation and decapsulation take 471,695, 30,112 and 500,827 compressions at HEP-QC-5 and 1,606,558, 201,148 and 1,804,827 at HEP-QC-7. State updates are 50% of the compressions in key generation and 44% to 47% in decapsulation. `H(ek)` over the public key is 28,946 and 197,570 compressions.
- Not counted: rejected samples, except the expected 1/0.2888 attempts of the matrix loop; the calls to `G` and the seed-splitting hash; all work that is not SM3. Table 5.1 (physical p. 19) gives timings and was not used.
- Source paths: `common/` and `ref/` are under `Implementations/Implementations/`, and `Lib/` is under `Implementations/`. The x86_64 build uses the same `common/` files.
