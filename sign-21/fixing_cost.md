## Attacks considered

## Remediation

- **sign-21-1, sign-21-2.** Both findings have one root cause. Within one signature every `TCCR(r, s, iv)` call of the pcGGM tree uses the same `(s, iv)`, and every `LeafHash` call is `PRG(x, iv, 0^8; 2λ)`, so one guess is tested against all revealed nodes or all hidden-leaf commitments. The costed repair gives each call its own tweak: the node index `id` for TCCR in BAVC.Commit, BAVC.Open and BAVC.Verify, and the leaf index for the PRG call in LeafHash. It is the first fix in the original post, which names both TCCR and the leaf PRG, and the team accepts it for TCCR ("using node indices for the TCCR tweaks (same as FAEST v2)"); the report notes that a change to the tree expansion alone does not separate `LeafHash`. The multi-target gain comes from shared hash inputs and not from the regular-syndrome-decoding problem, so no parameter changes. Scope: Function, specification and code: one more input to TCCR (§4.9.8) and to LeafHash (§4.4.7), and the index passed at their call sites. The reference tree expander already holds `id`, and its PRG has a tweak argument that LeafHash sets to 0; the optimized code computes the node index and receives leaf tweaks, and discards them. Impact: none (count). The verifier already computes every node and leaf index, so nothing is added to the signature. No cipher call is added: every TCCR call already keys the cipher with part of its own input and runs its own key schedule, and a tweak that is combined with the 120-bit `iv` or put in zero padding leaves the number of `Enc` calls unchanged. The proposals do not fix where the tweak enters the cipher input. The TCCR key has 32, 0, 0 and 128 padding bits at λ = 160, 256, 384 and 512, so at 256 and 384 the tweak has to be combined with the `iv`. That encoding, and the per-tweak query term of Theorem 8.12 under it, were not checked. The post's alternative, raising λ by ceil(log2(T_open)) + 1 bits, is not costed. It is a Parameter set change, and the specified ciphers leave no room for it: PRG needs n_k ≥ λ, which AES-256 and SHACAL-2 meet with equality at 256 and 512, and TCCR needs n_k + n_b ≥ λ + 128, which Rijndael-256 meets with equality at 384.
