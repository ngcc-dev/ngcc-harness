## Attacks considered

- sign-24-1: Chunked Reed–Solomon encoding reveals the signing witness (Implementation, Confirmed)

## Remediation

- **sign-24-1.** The root cause is that `RS_encode` splits the padded vector into 32 chunks and encodes each as its own short code, so the random tail does not hide the early chunks. The specification commits to one codeword of the whole padded vector (Algorithm 4.1, physical p. 19). The repair is the team's proposal: one global code of dimension N′ and length N in every parameter set, with the evaluation domain stated in the specification. The signature format does not change, because N, Q_VC and the Merkle layout stay. What the repair costs depends on the encoder. The team's posts do not name one, and its revised code was not read. The costed repair encodes the global code with a transform over a domain that supports one, which is a standard technique for Reed–Solomon codes of this length (additive FFT over a binary field: Gao and Mateer, IEEE Trans. Inf. Theory 56(12), 2010; Lin, Chung and Han, FOCS 2014). It is the cheapest credible repair. A radix-2 transform of length 2^11, 2^13 and 2^15 has 112,640, 851,968 and 7,864,320 butterflies per call with one multiplication in GF(2^16) each, against 216,320, 1,806,336 and 24,920,064 multiplications in the submitted call: 0.52, 0.47 and 0.32 of it (estimate). Signing makes two calls and the reference verifier one. Scope: Sub-algorithm, specification and code. The encoder in `rsencode.c` is replaced in the reference and optimized trees, `RS_encode` loses its chunking, and the specification fixes the domain L, which it leaves abstract. The powers of the generator at which the submitted encoder evaluates support no radix-2 transform, because the multiplicative group of GF(2^16) has odd order. Impact: none (estimate). Not counted: the additions of the transform, two per butterfly against one per Horner step (1.04, 0.94 and 0.63 of the submitted call), the conversion from the coefficient basis of Algorithm 4.1, and the larger encoder code and tables. The submission has no such encoder: its transforms cover only the unused shapes 11→44, 17→136 and 18→144. None was written or measured here. The alternative keeps the Horner loop of the submitted code, one multiplication per input symbol and output symbol, and is a Function repair. One call then costs 6,146,560 multiplications at 128 (×28.4), 54,246,528 at 256 (×30.0) and 785,981,952 at 512 (×31.5) (count). Charging one cycle per added multiplication against Table 3, which is a bound and not a predicted timing, signing would slow by at least 73%, 75% and 119% and verification by at least 85%, 100% and 165% (estimate). The answer would be Yes if the global code had to be encoded that way. A verifier that runs the Horner loop only at the Q_VC opened positions, as the submitted optimized verifier already does for its chunks, would need 2.90, 0.99 and 0.41 times the multiplications of the submitted reference call.
- **sign-24-2.** The root cause is that ζ is one 16-bit word that may be zero, which removes the mask ζ·F from the response G = E + ζ·F. The costed repair is the team's proposal: take the first nonzero word of the `polyres` stream and state that rule in the specification. Scope: Single line, specification and code (`hash_to_rand_PolyRes`; Algorithm 6.2, physical p. 34, gives neither the width of ζ nor a nonzero rule). Impact: none (count). A word is zero with probability 2^-16, so signing and verification read 2^-16 extra words on average. The team reports unchanged serialized formats and unchanged test vectors (as reported, not evaluated). The repair keeps ζ at 16 bits; the report records no attack on a nonzero ζ, and none was looked for here.
