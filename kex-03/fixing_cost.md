Yes: no costed repair is recorded for the BiT-128 signer leak (kex-03-9), so its impact on the six BiT-128 instances is not bounded, and the hash-input repairs (kex-03-2, kex-03-4) add 46% to 82% to the SM3 calls of the S2K initiator's Der step.

Impact: not bounded
Scope: Sub-algorithm (large), specification and code
Assessed: 2026-11-23

## Attacks considered

- kex-03-1: Bits-versus-bytes error reduces the ephemeral secret to 64 bits (Implementation, Confirmed)
- kex-03-2: Omitting signatures from the KDF breaks transcript matching (Design, Confirmed)
- kex-03-4: Initiator length-unit error removes the NAXOS long-term-key binding (Implementation, Confirmed)
- kex-03-7: K2K-PLAC512 encryption coins depend on only 128 message bits (Implementation, Confirmed)
- kex-03-9: The embedded BiT-128 signing oracle enables credential recovery and impersonation (Design, Confirmed)

## Remediation

- **kex-03-1.** Pass the input length in bits, `SEED_BYTES * 8`, in the responder's `pseudoXOF` call, so that all 64 drawn bytes are absorbed. The specification is sound: `wEncaps` and the generic `2Encaps` use fresh randomness (Figures 1, 2, 4 and 7, physical pp. 8, 9, 11 and 13). Scope: Single line, code; the same argument in the 23 files that the report lists. Impact: none. No object changes: the encrypted message is `MSG_LEN_BYTES` = 16, 32 or 64 bytes, the width of the level, so the plaintext does not have to grow. The call makes 3 or 4 more SM3 calls per session (count). The team's reply under Proposed fixes says the length arguments are corrected in a revision; it gives no sizes or timings.

- **kex-03-2.** Add the transmitted signature bytes to the KDF input, in the last KDF step of Figures 1, 2 and 4 and in `derive_session_key` of the 18 signature-bearing instances. This is the authors' revised KDF recorded under Proposed fixes. Scope: Function, specification and code. Impact on bandwidth: none, because both parties hold the signatures. The S2K and S2S initiator derives the key in a later step than it signs, and BiT signing is randomized, so it must keep its own signature or a digest of it in the session state; the state is not transmitted. Impact on speed: the KDF input grows by 1,504, 3,456 or 6,695 bytes per signature, which is +44% to +51% for K2S and S2K and +90% to +105% for S2S (count). The effect on a step is counted under kex-03-4. The framework-and-role tags that the team also announces add a constant and are not costed.

- **kex-03-4.** Pass the input length in bits, `(SEED_BYTES + SKI_LEN) * 8`, in the initiator's two `G(r‖sk_i)` calls, as Figures 2 and 4 specify (`wGen(G(sk_i, r̃))`). Scope: Single line, code; two calls in each of the 12 S2K and S2S instances, in both trees. The submitted code skips specified work here: it absorbs 241, 528 or 1,136 bytes at the three levels, and the corrected call absorbs 1,928, 4,224 or 9,088 (count). Impact: no bytes. Together with kex-03-2, the SM3 calls in the S2K initiator's Der step rise from 137 to 215 at S2K-BiT128-PLAC128 (+57%) and by +46% to +82% over the six S2K instances (count). That step is `G`, `wGen`, `wDecaps` and the KDF, with no signature operation. The count takes each `wGen` sampler once; a resampled polynomial adds the same calls before and after, so the percentages are lower in such a run (+35% to +65% if every `wGen` call is made twice). Counted in bytes for a hash that absorbs each input once, the rise is +60% to +88% (count). The polynomial work of the step does not change and was not counted in the same unit, so the step as a whole rises by less; it is judged to rise by more than 10% (judgment). The step is the smaller of the initiator's two: Table 6 (physical p. 30) gives it 69.73 µs of 686.37 µs online at S2K-BiT-PolarLAC-128. Steps that contain a signature operation (the Init steps, the responder steps, the K2S and S2S Der steps) hash more and change less; they were not counted. The team's reply records the correction without sizes or timings.

- **kex-03-7.** Pass `sizeof(buf3) * 8` in the two `pseudoXOF` calls of each 512-bit PLAC K2K tree, so that the 64-byte message and the public-key digest are absorbed as Figure 9 specifies (physical p. 14). Scope: Single line, code. Impact: none. No object changes, and each `2Encaps` or `2Decaps` makes 12 more SM3 calls (6 to 18), against 856 in the K2K-PLAC512 KDF alone (count). The neighbouring `pseudohash(…, buf, sizeof(buf), …)` call passes a byte count in the same way; the finding does not cover it and it is not costed.

- **kex-03-9.** The root cause is in the embedded signer: one sign bit `b` is drawn per signature and applied to the whole response, while rejection is decided for each coefficient separately. A repair has to make the accepted response independent of that shared sign. That means a rejection step over the whole response in BiT-128, or a different signature in the six BiT-128 instances, which the frameworks allow because they use only the signature interface (physical p. 17). The report records no proposed fix for this finding. The first route stays closest to the design, and no parameters, sizes or repetition counts are stated for it. The second depends on the signature chosen, and the specification names none. Scope: Sub-algorithm, specification and code (Figure 12, physical p. 15, and the signer's `sign.c` and `sample.c`). Impact: not bounded. A new rejection rule changes the expected number of signing repetitions and may change the mask and bound widths that fix the signature size; a different signature changes the signature and the long-term public key. No value for the first route can be taken from the specification, the source or the report, and no estimate was made. For scale, the BiT-128 signature is 1,504 of the 2,016 bytes of the smallest message that carries one, so a signature 13.4% longer moves that message by 10%; the BiT public key is itself a published object of 1,048 bytes. As an anchor for the second route, ML-DSA-44 has a 2,420-byte signature and a 1,312-byte public key (FIPS 204, Table 2), 60.9% and 25.2% above BiT-128 (count); its signing and verification work was not counted. A limit on signatures per key is not a repair, because the reported recovery uses about 250,000 signatures, far below 2^64. BiT-256 and BiT-512 have the same structure but are not listed as affected, so they are not costed.
