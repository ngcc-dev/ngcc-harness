## Attacks considered

- sign-02-1: A 512-bit unsalted message representative caps forgery security at 256 bits (Design, Confirmed)
- sign-02-2: A shared bimodal sign leaks an equivalent BiT-128 signing key (Design, Confirmed)
- sign-02-3: Mask-seed collisions recover an equivalent BiT-128 signing key (Design, Probable)

## Remediation

- **sign-02-1.** Root cause: BiT-512 signs the fixed 512-bit digest µ = H(tr ‖ M), so two messages with one µ share every signature. The costed repair is the submitters' proposal, as recorded in the report and not evaluated: the message and its encoded length enter the Fiat–Shamir challenge hash in place of the prehash. It changes the challenge derivation of Figure 5, Sign lines 4 and 11 and Verify lines 4 and 8, and Sign line 7 where µ also seeds the masks. Scope: Function, specification and code. Impact: none. µ is hashed and never sent, and the signature stays c̃ ‖ z1,0 ‖ z1,1 ‖ h at 6,695 bytes. For a message of up to 64 bytes each challenge hash absorbs at most 72 bytes more than the submitted 1,984, beside 25,600 bytes of mask expansion per full resample, and the separate µ hash goes away. A long message would then be absorbed in every signing attempt, where the submitted code hashes it once. The revision hashes tr ‖ LE64(|M|) ‖ M ‖ Encode(w1), with the message ahead of w1 (specification v2.1, §3.7, physical p. 19), so the state after the message can be kept across attempts; whether its code does so was not checked. For long messages the figure therefore rests on the cheaper standard repair, widening µ to 1,024 bits, which hashes the message once and also adds no byte. The contest hash of the default build has a 1,024-bit digest, and the SHA3-512 of the optional SHAKE build already has a 1,024-bit capacity, so the hashing rate stays as it is.
- **sign-02-2.** Root cause: one sign bit b is shared by the whole response, while RejectSample corrects each coefficient against a scalar mixture (Figures 3 and 4), so the joint response keeps correlations that depend on the key. The costed repair is the submitters' revision, as their specification v2.1 of 2026-11-06 states it and not evaluated: rejection against a parabolic target over the joint response vector, parabolic masks, retuned parameters (q = 7681 / 7681 / 25601, γ1 = 8100 / 15400 / 66000, Table 11) and the complete public key b in place of b1 (physical pp. 4, 20 and 36). A repair that replaces the rejection step and keeps the compressed key is not taken as credible, because the finding records the submitters' statement that the compressed key leaks as well and their proposal removes the compression. Scope: Parameter set, specification and code: the rejection step is replaced and the parameter tables are redone. The public-key encoding changes. Impact, from the revision's stated sizes and its stated reference timings, which were taken on the platform and with the compiler flags of the submitted Tables 7 and 8: public key +20.6% / +17.9% / +15.2% at BiT-128 / 256 / 512 (count); signature −4.3% / −13.9% / +11.6% (count); signing +67% / +179% / +82% in the SM3 build and +1% / +89% / −2% in the FIPS 202 build; key generation +43% / +14% / +20% and +114% / +117% / +121%; verification +5% / −17% / −9% and +33% / +18% / +20% (estimate). The stated acceptance rates rise from 18% / 53% / 33% to 61% / 53% / 74%, so the expected signing attempts fall from 5.6 / 1.9 / 3.0 to 1.6 / 1.9 / 1.4, and the slower signing comes from more work per attempt. The BiT-512 figures include the revision's change for sign-02-1. These are the revision's statements, quoted and not evaluated: its signature size was not reproduced from a formula, and its code was not downloaded, built or run. Sending the complete b at the submitted moduli would instead add 39% / 54% / 46% to the public key (count), with the effect of a new rejection step on the signature and on signing not bounded; the revision is the cheaper credible repair for the public key and the only one with bounded figures. Not checked: whether the revised parameters meet the levels claimed for them; the leak through the compressed key, for which the report has no witness.
- **sign-02-3.** Root cause: at BiT-128 the 128-bit seed_y alone determines the masks of a signing call, so two calls with equal seeds on different messages reveal s0. A stated limit of 2^64 signatures per key is not a repair, because the report gives 10.3% success at 2^64 signatures. The costed repair widens seed_y, and the randomness rnd that it is derived from, to 2κ = 256 bits at BiT-128, the usual repair of a narrow secret seed; under the finding's model the expected number of usable pairs at the 2^80 budget is then 2^-99, and 205 bits is the smallest width that keeps the attack at 2^128 there. rnd widens with the seed because seed_y = XOF(ρ′ ‖ rnd ‖ µ) takes only as many values as rnd when one message is signed again, while the sign bit b is drawn separately; the finding's difference equations then hold with c = c′ and b ≠ b′. The report's witness uses different messages and does not record this case. Scope: Function, specification and code: the lengths in Sign lines 6 and 7 of Figure 5. In the code the mask seed and rnd need their own length, because `BIT_SEEDBYTES` also sizes the public seed ρ. Impact: none. Neither value is sent; signing draws 16 more random bytes, and each mask and rejection stream absorbs 16 more bytes. Raising the shared constant instead would add 16 bytes to the public key (+1.5%). The report records no proposed fix for this finding. The revision still derives the mask seed ρ″ = H(K ‖ µ) with κ = 128 bits at BiT-128 (Figure 7, physical p. 20), so the widening is costed on top of it; there too the seed is not sent. BiT-256 and BiT-512 are outside the finding and are not changed.
