## Attacks considered

- sign-14-1: A degenerate QuickSilver witness gives universal public-key-only forgeries (Design, Confirmed)
- sign-14-2: A shared TCCR tweak enables one-signature multi-target key recovery (Design, Confirmed)

## Remediation

- **sign-14-1.** Root cause: at 256, 384 and 512 bits the degree-2 relation does not enforce v1 ≠ 0 and k ≠ c3, so it holds on the branch v1 = 0, k = c3 without a Lynx preimage. The costed repair is the submitters' proposal, as their targeted-modification note of 2026-09-29 states it: S1 and S2 become inversion at every level, the factor (k + c3)^-1 and the constant c3 are dropped, and the three constraints become v1(k + c1) = 1, v2(L0(k) + c2) = 1 and L1(v1)·L2(v2) + L3(k + v1 + v2) = t. Scope: Construction, specification and code: the one-way function is redefined at all four levels, which changes the hardness assumption, while the VOLE, BAVC and Fiat–Shamir layers stay. Impact: none. The witness stays (k, v1, v2), 3λ bits, and the degree stays 2, so Eq. (4) gives the submitted sizes. There are still three degree-2 constraints, now without the Frobenius matrix products of the submitted S-boxes, and the note says that performance is "essentially unaffected". These are the proposal's statements, as reported and not evaluated. An alternative that keeps the submitted S-boxes adds an inverse witness for each of the two unenforced nonzero values: 2λ more witness bits, 2λτ bits per signature, +11.5% at 256s to +15.1% at 512f (count). It is not the costed repair, because the proposal is cheaper; with it the answer would be Yes. Not checked: the note's claim that the Lynx cryptanalysis is unchanged, including the algebraic estimates of Table 14 (physical p. 63) for two inversion S-boxes; the revised ePrint 2026/1099, whose PDF could not be fetched (HTTP 403) and of which only the abstract page was read.
- **sign-14-2.** Root cause: every TCCR call of one signature uses the same tweak (s, ivsig), so all opened nodes are targets of one enumeration. The costed repair is the recorded proposal: node-index tweaks (the team), with the index an actual TCCR input (Xiong and Wang). Scope: Function, specification and code (TCCR in Section 5.9.8 and its calls in BAVC.Commit and BAVC.Verify). Impact: none, provided the index shares the existing tweak field. TCCR stays two cipher calls under one key, that key already changes with every node, and the index is the public node position, so nothing is sent. Not checked: how the revision encodes the index. At 256 and 384 bits the cipher key xR ∥ ivsig has no spare bit, so the index has to be combined with the 120-bit ivsig; a wider tweak would need a larger cipher or a further call, which is not costed.
- **sign-14-3.** Root cause: LeafHash calls PRG(x, ivsig, 0^8; 2λ) for every leaf, so one guess applies to all τ published leaf commitments. The costed repair is the reporters' proposal: include the leaf index in LeafHash. Scope: Function, specification and code (Section 5.4.7 and the PRG input of Section 5.9.9). Impact: none, under the same proviso. The PRG block ivsig ∥ counter is full at a 128-bit block size, so the index has to be combined with ivsig, and the number of cipher calls per leaf stays ⌈2λ/nb⌉. The index is public and nothing is sent.
