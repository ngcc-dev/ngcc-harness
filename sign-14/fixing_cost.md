## Attacks considered

- sign-14-1: A degenerate QuickSilver witness gives universal public-key-only forgeries (Design, Confirmed)
- sign-14-2: A shared TCCR tweak enables one-signature multi-target key recovery (Design, Confirmed)
- sign-14-3: Fixed leaf-commitment tweaks enable multi-target key recovery (Design, Confirmed)

## Remediation

- **sign-14-1.** Root cause: at 256, 384 and 512 bits the degree-2 relation does not enforce v1 ≠ 0 and k ≠ c3, so it holds on the branch v1 = 0, k = c3 without a Lynx preimage. The costed repair is the submitters' proposal, as their targeted-modification note of 2026-09-29 states it: S1 and S2 become inversion at every level, the factor (k + c3)^-1 and the constant c3 are dropped, and the three constraints become v1(k + c1) = 1, v2(L0(k) + c2) = 1 and L1(v1)·L2(v2) + L3(k + v1 + v2) = t. Scope: Construction, specification and code: the one-way function is redefined at all four levels, which changes the hardness assumption, while the VOLE, BAVC and Fiat–Shamir layers stay. Impact: none. The witness stays (k, v1, v2), 3λ bits, and the degree stays 2, so Eq. (4) gives the submitted sizes. There are still three degree-2 constraints, now without the Frobenius matrix products of the submitted S-boxes, and the note says that performance is "essentially unaffected". These are the proposal's statements, as reported and not evaluated. An alternative that keeps the submitted S-boxes adds an inverse witness for each of the two unenforced nonzero values: 2λ more witness bits, 2λτ bits per signature, +11.5% at 256s to +15.1% at 512f (count). It is not the costed repair, because the proposal is cheaper; with it the answer would be Yes. Not checked: the note's claim that the Lynx cryptanalysis is unchanged, including the algebraic estimates of Table 14 (physical p. 63) for two inversion S-boxes; the revised ePrint 2026/1099, whose PDF could not be fetched (HTTP 403) and of which only the abstract page was read.
- **sign-14-2.** Root cause: every TCCR call of one signature uses the same tweak (s, ivsig), so all opened nodes are targets of one enumeration. The costed repair is the recorded proposal: node-index tweaks (the team), with the index an actual TCCR input (Xiong and Wang). Neither fixes the encoding, so the costed one is this: BAVC.Commit, BAVC.Open and BAVC.Verify pass the tweak ivsig ⊕ IntToBits(id; 120) where they now pass ivsig, with id ∈ [1, L) the node position. TCCR itself (Section 5.9.8) keeps its key x_R ‖ tweak ‖ 0^(n_k + n_b − 128 − λ) and its plaintext i ‖ x_L. For one signature id ↦ ivsig ⊕ id is one-to-one, so no two nodes share a tweak, and each tweak stays uniform over 2^120 values. XORing a counter into a fixed random IV is the usual per-record nonce construction (RFC 8446, §5.3); how FAEST v2, which the team cites, encodes its tweak was not checked. Scope: Function, specification and code (the TCCR calls in BAVC.Commit, BAVC.Open and BAVC.Verify; TCCR itself is unchanged). Impact: none. TCCR stays ⌈λ/n_b⌉ = 2 cipher calls under one key, that key already changes with every node, and the index is the public node position, so nothing is sent. The index needs 13 to 18 bits. At 160 and 512 it would also fit, without XOR, in the 32 and 128 zero bits of the TCCR key. At 256 and 384 the key x_R ‖ ivsig and the plaintext i ‖ x_L are full (n_k + n_b = λ + 128) and the byte i leaves 7 spare bits, so a concatenated (ivsig, id) would need a further cipher call or a wider cipher; that variant is not the cheapest and is not costed. Theorem 9.12 (physical p. 111) bounds the TCCR advantage by 4 q_E µ/2^ρ + q_C(µ − 1)/2^n, with µ the largest number of construction queries on one tweak; the submission has µ = 3L/2 − 1 in every signature. With the XOR encoding a tweak value can repeat only between signatures, and at 2^64 signatures µ stays at 3 positions (6 queries) or below, against 2 positions for a concatenated encoding (Evidence). A full proof under the encoding was not checked.
- **sign-14-3.** Root cause: LeafHash calls PRG(x, ivsig, 0^8; 2λ) for every leaf, so one guess applies to all τ published leaf commitments. The costed repair is the reporters' proposal: include the leaf index in LeafHash. With the same encoding, LeafHash passes ivsig ⊕ IntToBits(id; 120) to PRG, with id ∈ [L, 2L) the leaf position, so leaf tweaks differ from each other and from the node tweaks. Scope: Function, specification and code (Section 5.4.7, and the PRG input of Section 5.9.9, which is unchanged). Impact: none. The counter-mode block stays tweak ‖ (t + i) ‖ 0^(n_b − 128) and the number of cipher calls per leaf stays ⌈2λ/n_b⌉ = 3, 4 and 4 at 160, 256 and 512, and two TCCR evaluations at 384. At 160 and 512 the index would also fit in the 32 zero bits of the PRG key or the 128 zero bits of the block; at 256 the block ivsig ‖ counter is full. The index is public and nothing is sent.
