No: indexing the tree and leaf hashes adds no work, and giving H1 a 1024-bit capacity at the two 512-bit sets adds 3.5% to the Keccak-f calls of GreatWall-512 signing and verification without changing any size.

Impact: signing +1% to +3.5% at GreatWall-512s (estimate); verification +1% to +3.5% at GreatWall-512s (estimate)
Scope: Sub-algorithm (large), specification and code
Assessed: 2026-11-23

## Attacks considered

- sign-13-1: SHAKE256 capacity reduces GreatWall-512 forgery cost to about 2^256 (Design, Confirmed)
- sign-13-3: Unindexed internal GGM nodes enable multi-target seed recovery below the claimed levels (Design, Probable)
- sign-13-4: Unindexed leaf commitments enable multi-target seed recovery below the claimed levels (Design, Probable)

## Remediation

- **sign-13-1.** Root cause: H1 is specified as a collision-resistant hash with 2λ output bits and is instantiated at λ = 512 with SHAKE256, whose capacity is 512 bits. The team's response, as the report records it, promises to clarify the hash requirements and gives no construction or figures to cost. The costed repair is the standard one for a narrow hash: at the 512-bit sets, H1 runs on a Keccak-f[1600] sponge with a 1024-bit capacity, so its rate falls from 1088 to 576 bits. Scope: Sub-algorithm, specification and code: Section 2.3.4 names SHAKE256 for every hash above λ = 128, and the code selects it in one place for all hashes. No transmitted object changes: µ, the per-vector digests, the root commitment and hV are recomputed by the verifier and never sent, and the leaf commitments in the opening are H0 outputs that are already 2λ bits. Impact: H1 needs 1088/576 = 1.89 times as many permutations per byte. It absorbs 128 bytes per leaf, which the submitted code hashes among about 24 Keccak-f calls per leaf, so the calls per signature rise by 3.49% at 512s and 3.52% at 512f (count). The time rises by at most that share, because the field arithmetic is unchanged. The stated timings bound the Keccak share of signing at 28% (reference) and 54% (optimized) for 512f and at 71% and 91% for 512s, so the increase is at most +1.0% to +1.9% at 512f and +2.5% to +3.2% at 512s; the header gives +1% to +3.5% (estimate). Verification hashes the same H1 input and has the same ratio. Hashing a long message into µ costs 1.89 times as much per byte and is not in these figures. Not costed: a wider sponge for the other SHAKE256 calls at λ = 512. The Fiat–Shamir hashes absorb under 20 KB per signature and would not change the figure. The tree, leaf and VOLE generators, which the 512-bit code also builds on SHAKE256, absorb one block of 81 bytes per call, and the collision in the report needs a second block. That input no longer fits one 72-byte block, so moving all three would about double the Keccak-f calls and would change the answer to Yes; moving the leaf hash H0 alone would add 8.4% to the calls, 11.8% with H1, which is borderline. The finding's root cause is the collision resistance of H1, and only that is costed.
- **sign-13-3.** Root cause: every internal node is expanded by the same map PRG(K ∥ ivvole; 2λ), so one guess applies to every opened seed of a signature. The costed repair is the standard separation of hash inputs: the node position enters the PRG call as a tweak. Scope: Function, specification and code (Algorithm 4 line 15 and the matching step of Algorithm 14; `expand_chunk`). Impact: none. In the AES sets the tweak is combined with the 128-bit counter block that already carries the IV, and in the 512-bit code it is absorbed in the same SHAKE256 block, so no cipher or permutation call is added. The position is public and nothing is sent. The report records no proposed fix.
- **sign-13-4.** Root cause: H0(K ∥ ivvole) has no leaf position, so one guess applies to all τ published leaf commitments. The costed repair is the same separation: H0 also absorbs the leaf position. Scope: Function, specification and code (Algorithm 4 line 20, Algorithm 14 line 36 and the input width of H0 in Section 2.3.4; `write_leaf` and the leaf generator). Impact: none. The input K ∥ iv ∥ 0x00 is 33 to 81 bytes against a rate of 168 or 136 bytes, so a few more bytes stay in one block, and nothing is sent. The report records no proposed fix.
