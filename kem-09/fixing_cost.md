## Attacks considered

- kem-09-4: The rejection key hashes the re-encryption instead of the received ciphertext (Implementation, Confirmed)

## Remediation

- **kem-09-1.** Expand the comparison result to `0x00` or `0xff` before the select, as the report states. The code negates an arbitrary nonzero byte (`KEM_Cheetah.c:290`). Algorithm 20 replaces the whole key on mismatch, so the specification is sound. Scope: Single line, code, in the twelve `KEM_Cheetah.c` files. Impact: none.
- **kem-09-4.** Compute the rejection key over the received ciphertext, `H(salt‖c)`, as Algorithm 20 line 4 specifies and the report states. The code re-encrypts into the hashed buffer (`:277`) and hashes `salt‖c′` (`:283`). Scope: Function (`kem_dec`), code. Impact: none. The code already hashes `SEED_BYTES + CIPHERTEXT_BYTES` bytes once per call; the repair changes which ciphertext is in that buffer. The re-encryption then needs its own buffer, 864 to 4,032 bytes of stack.
- **kem-09-5.** Choose new parameters for Cheetah128 and Cheetah256 so that the failure attack reaches the level and the failure rate, computed with the public-key rounding term, is within Table 2 again. A stated limit of 2^64 decapsulations per key is not a repair: the Cheetah256 attack needs 2^63.1 queries. (At Cheetah128 the same limit would leave the model's attack at 2^184.3 encapsulations.) The specification says that η and (d_b, d_u, d_v) are set by the failure formula and the security formulas, so those are the free parameters. The smallest change found is to η alone: 5 to 3 at Cheetah128 and 4 to 1 at Cheetah256. By the finding's exact law the failure rates are then 2^-146.3 and 2^-260.4, against Table 2's 2^-129 and 2^-176. Under the finding's boosting model, with 1,500 failures within 2^80 queries and no margin, the attack then costs 2^703.5 encapsulations at Cheetah128, and at Cheetah256 no preselection reaches the query budget. One step less of η does not meet Table 2: η = 4 and η = 2 put the attack at 2^224.6 and 2^733.4 encapsulations, but the failure rates are 2^-103.3 and 2^-120.2. Scope: Parameter set, specification and code (Table 2, the failure analysis, and `ETA` in `params.h`). Impact: none. No size formula contains η, and the noise XOF output of 2kNη/8 bytes per vector shrinks. This is a one-sided lower bound, and the finding is Probable; the scope rests on it alone. The report records no proposed fix. What the lower η uses up: by the specification's primal condition the full-dimension estimate falls from 2^148.3 to 2^138.4 at Cheetah128 and from 2^325.9 to 2^275.4 at Cheetah256, above the levels. One estimator run gives dual-hybrid 2^134.8 and 2^258.7, which is 2.7 bits above the level at Cheetah256. The specification's own Table 4 values (159 and 307) could not be reproduced from that condition, so its margin at the lower η is not known. The quotient estimate of kem-09-2 (High, Lead, not costed) moves from 2^27.7 to 2^25.1 and from 2^67.7 to 2^57.2. What would tip the answer is Cheetah256. If η = 1 is not accepted there, the smallest point found within Table 2 is η = 2 with (d_b, d_u, d_v) = (11, 10, 5) (2^-197.7; public key +9.71%, ciphertext +1.85%). The specification also chooses d_u so that the rounding error of u stays within ±η (physical p. 16). The exact law does not need that rule, but if it is kept the smallest points found are η = 4 with (10, 10, 8) at Cheetah128 (2^-129.8; ciphertext +7.41%) and η = 2 with (11, 11, 4) at Cheetah256 (2^-302.9; public key +9.71%, ciphertext +9.26%).
