No: the four findings are repaired by code corrections in the 256-, 384- and 512-bit sets and one stated hash length (a wider `mu`, wider secret seeds, a hash wrapper that keeps its whole input, and the challenge sampler of Figure 1), which change no transmitted object and add less than 1% of work to signing or verification.

Impact: none
Scope: Function (small), specification and code
Assessed: 2026-11-23

## Attacks considered

- sign-06-1: The implemented message representative caps forgery security at 256 bits (Implementation, Confirmed)
- sign-06-2: The implementation expands the entire key pair from a 256-bit root (Implementation, Confirmed)
- sign-06-5: A byte-wide position index and 64 sign bits shrink the 384- and 512-bit challenge spaces below their levels (Implementation, Confirmed)
- sign-06-6: The SHAKE wrapper compresses the message-representative input to 256 bits (Implementation, Confirmed)

## Remediation

- **sign-06-1.** Widen `mu` from 64 bytes to twice the level, 96 bytes at 384 and 128 bytes at 512, and state the output length of `H` in the specification, which leaves it open (physical pp. 10–12). This is cheaper than a salt, which would add signature bytes. `mu` is only hashed, into the mask seed and the challenge (`sign.c:122–128,159–163,404–408`), and is not sent. Scope: Single line, specification and code (`CRHBYTES`, `params.h:7`, set per level). Impact: none; the calls that produce and absorb `mu` handle 32 or 64 more bytes.
- **sign-06-2.** Draw the key-generation seed at the `n` = 512 bits that Algorithm 1 specifies (physical pp. 9–10), and widen the signing key `K` from 32 bytes to 48 or 64, or draw the `n`-bit per-signature seed of Algorithm 2 (physical p. 12). The specification is sound on both points and stays. Both values are secret. The private seed `rhoprime` is already 64 bytes (`sign.c:28,40–41`), and the public seed `rho` stays at the 32 bytes that the Table 2 sizes assume. Scope: Function, code (`sign.c:27–41,122–128` and the secret-key layout, `packing.c:101–117,134–149`; `SEEDBYTES` is shared with `rho` and has to be split). Impact: none on transmitted objects; the private key grows by the 16 or 32 bytes of `K` (3136 and 4608 bytes in Table 2).
- **sign-06-5.** Make `poly_challenge` follow Figure 1 (physical p. 8): positions drawn from {0,…,i} for `i` up to 511, and a fresh sign bit for each of the `tau` coefficients (`poly.c:870–902`). The specification stays. `tau`, the bounds and the signature format do not change, and the rejection formula of §3.4 (physical p. 16) has no term for the positions or signs of the challenge. Scope: Function, code. Impact: none; the sampler needs about 179 or 288 XOF bytes instead of one 136-byte block, which is +0.5% and +0.6% of the XOF output of signing and +0.2% and +0.3% of that of verification at 384 and 512. The corrected sampler reads past the first block and needs a squeeze that continues the stream; the submitted `fill_squeeze` restarts it (`symmetric-shake.c:26–29`; sign-06-4, High, not costed). Not checked: the rejection rate of the corrected sampler by experiment.
- **sign-06-6.** Make `shake128_absorb` and `shake256_absorb` keep the whole input, so that `mu = H(pk || m)` is one hash of its input as the specification writes it (`symmetric-shake.c:57–74,151–167`). The same routine also serves `tr = H(pk)` and the challenge hash. Scope: Function, code. Impact: none. A message of up to 446 bytes never reaches the compression step, and for longer input the submitted wrapper already hashes 512 bytes for every 480 new bytes, which is more than a single pass. With the contest's one-shot `pseudoXOF` the wrapper then holds the whole input in memory, against 512 bytes as submitted; an incremental XOF does not need this. Keeping the chained wrapper with a carry of twice the level would instead cost 7%, 15% and 25% more hash calls per message byte at 256, 384 and 512; that affects long messages only and is not the costed repair. Not checked: the top-level source copies, which the per-set builds do not use.

## Evidence

- Baseline: Table 2 (physical p. 15) gives public keys of 5792 and 7648 bytes and signatures of 7344 and 9024 bytes at 384 and 512. Control with Table 1 and `params.h:160,170`: 32 + 5·512·18/8 = 5792, 48 + 6·512·19/8 = 7344, 32 + 7·512·17/8 = 7648, 64 + 7·512·20/8 = 9024.
- The transmitted objects are `rho`, `t1`, the challenge hash and `z`. `mu`, the seed and `K` are in none of them, and no repair changes the challenge hash (48 and 64 bytes) or `z`. §2.3.1 (physical p. 9) calls `rho` an `n`/8-byte seed, which would be 64 bytes at `n` = 512 and +0.6% on the 384 public key; sign-06-2 does not need it.
- Hash: the per-set trees send all hashing to the contest's `pseudoXOF` (`symmetric-shake.c:26,69,104,162,191,262,284`), so calls and bytes are counted and an ideal XOF of the needed width is assumed.
- XOF output, from `symmetric-shake.c:258–264,280–286` and `poly.c:684–708,847–858`: 2048 bytes for each of the `K`·`L` matrix polynomials (61,440 and 100,352 bytes) and 1248 or 1376 bytes for each of the `L` mask polynomials in an iteration (7488 and 9632 bytes). With 3.25 and 2.99 iterations (physical p. 16), signing squeezes about 86,500 and 129,800 bytes and verification about 61,600 and 100,600.
- Challenge sampler: the submitted code squeezes one block, 160 bytes after rounding (`symmetric-shake.c:17–19`). With 2-byte position tries accepted with probability (i+1)/512, the expected tries are the sum of 512/(i+1): 84.5 for i = 434…511 and 136.6 for i = 392…511. With `tau` sign bits that is 179 and 288 bytes, so 2 and 3 blocks, +128 and +256 bytes per challenge. Signing: 3.25·128/86,500 = +0.5% and 2.99·256/129,800 = +0.6%. Verification: 128/61,600 = +0.2% and 256/100,600 = +0.3%.
- Rejection: 1 − exp(−n·l·tau·eta_s/gamma1 − n·k·tau·eta_e/gamma2) (physical p. 16) gives 0.669 and 0.641 with Table 1's values at 384 and 512, for the submitted and the corrected sampler alike.
- Challenge space with Figure 1, as the report computes it: 2^388.9 and 2^517.6, capped at 2^384 and 2^512 by the challenge hash (`python3 -B sign-06/reproduce_challenge_image.py`).
- Wrapper: a 512-byte buffer with a 32-byte carry takes 480 new bytes per call (`symmetric.h:9`, `symmetric-shake.c:160–165`). A carry of 64, 96 or 128 bytes would leave 448, 416 or 384: +7.1%, +15.4% and +25.0% calls.
