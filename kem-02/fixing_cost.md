No: the two decapsulation defects are repaired without added work, and replacing the four-call SM3 expansion of G by one call of a Keccak sponge of capacity 2λ costs no more than the four SM3 calls by a word-operation count at Amoeba-1728 and Amoeba-2304.

## Attacks considered

- kem-02-1: The FO check compares only every fourth ciphertext byte (Implementation, Confirmed)
- kem-02-6: Pre-FO decoder failures give a full chosen-ciphertext key recovery (Implementation, Confirmed)
- kem-02-8: Amoeba's four-call SM3 expansion has only a 256-bit internal state (Implementation, Confirmed)

## Remediation

- **kem-02-1.** Compare every ciphertext byte. `cmp` advances its index by four (`ccakem.c:19`); the repair is that stride, as the report states. §1.4 rejects when the re-encryption check fails, so the specification is sound. Scope: Single line, code, in ten byte-identical files. Impact: none. The loop compares 1,047 to 3,914 bytes instead of a quarter of them, next to hundreds of SM3 compression calls.
- **kem-02-6.** Do not return before the FO check. `CCAKEM_Decaps` returns -1 as soon as `CPAPKE_Decrypt` reports a decoder failure (`ccakem.c:61-63`, `cpapke.c:444-445`). The repair in the report carries that failure into the rejection decision, so that such a ciphertext receives the rejection key `KDF(z, ct)`. Scope: Function (`CCAKEM_Decaps`), specification and code. §2.3.2 says decryption is "explicitly rejected" on two errors, and §1.4 does not say what decapsulation then returns, so the specification must state it. Impact: none. A ciphertext that decodes takes the same path as before. Only a rejected ciphertext now runs G, the re-encryption and the KDF. The unbounded correction index (kem-02-4, High) is a separate check and is not costed.
- **kem-02-8.** Replace the four SM3-256 calls by one hash with 1024-bit output and an internal state wide enough for the level, applied to `(ID(pk), m)` as §1.4 defines G. The report names this replacement, and the specification says that its SM3 plug-ins "will need to be replaced" for the 512-bit level. The specification names no 1024-bit hash, so the repair is costed by its dimensions as one call of a Keccak sponge of capacity 2λ: 768 bits (rate 104 bytes) at Amoeba-1728 and 1,024 bits (rate 72 bytes) at Amoeba-2304. The contest's `pseudohash` as coded is not costed: its 1024-bit mode is itself built from 256-bit SM3 chains (`symmetric/auxfunc.c:353–444`), the root cause of the finding, and the ruleset treats it as a placeholder costed by calls and bytes. As coded it would take 27 SM3 compressions where G takes 12, +3.5% of the SM3 work of encapsulation at Amoeba-1728. Scope: Sub-algorithm, specification and code. In the code the change is confined to the two loops at `ccakem.c:40–45` and `66–71`. In the specification, the statement that SM3 instantiates Hash must name the 1024-bit construction. Impact: none. No transmitted object changes, because `m` is already 512 bits at every level. The sponge call absorbs 128 bytes and squeezes 128 bytes in 3 Keccak-f[1600] calls at both sets, against 12 SM3 compressions for the four submitted calls. By word operations one permutation is 1.8 to 3.6 SM3 compressions (64-bit or 32-bit words), so the repaired G is 5.4 to 10.7 compression-equivalents against 12 (estimate), and encapsulation and decapsulation do not grow. Encapsulation would grow by 1% only if one permutation cost more than 5.4 compressions (4.5 with the contest XOF idealized as below), and by 10% only above 18.2 (9.4). Key generation does not call G. Only Amoeba-1728 and Amoeba-2304 are affected; the 384-bit set is optional and could be withdrawn, but the 512-bit set needs the repair. Alternative with a named function: two SHA3-512 calls with a counter byte take 4 permutations, at most +0.5% of the as-built SM3 work of encapsulation at Amoeba-1728 (+1.4% with the XOF idealized). Not relied on: moving the counter in front of `m` in the four SM3 calls. Neither the report nor the submitters propose it, and it keeps four 256-bit chains where the specification asks for a 1024-bit hash. Not checked: a measured comparison of Keccak and SM3, and the optimized trees' hash code.
