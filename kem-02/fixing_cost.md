## Attacks considered

- kem-02-1: The FO check compares only every fourth ciphertext byte (Implementation, Confirmed)
- kem-02-6: Pre-FO decoder failures give a full chosen-ciphertext key recovery (Implementation, Confirmed)
- kem-02-8: Amoeba's four-call SM3 expansion has only a 256-bit internal state (Implementation, Confirmed)

## Remediation

- **kem-02-1.** Compare every ciphertext byte. `cmp` advances its index by four (`ccakem.c:19`); the repair is that stride, as the report states. §1.4 rejects when the re-encryption check fails, so the specification is sound. Scope: Single line, code, in ten byte-identical files. Impact: none. The loop compares 1,047 to 3,914 bytes instead of a quarter of them, next to hundreds of SM3 compression calls.
- **kem-02-6.** Do not return before the FO check. `CCAKEM_Decaps` returns -1 as soon as `CPAPKE_Decrypt` reports a decoder failure (`ccakem.c:61-63`, `cpapke.c:444-445`). The repair in the report carries that failure into the rejection decision, so that such a ciphertext receives the rejection key `KDF(z, ct)`. Scope: Function (`CCAKEM_Decaps`), specification and code. §2.3.2 says decryption is "explicitly rejected" on two errors, and §1.4 does not say what decapsulation then returns, so the specification must state it. Impact: none. A ciphertext that decodes takes the same path as before. Only a rejected ciphertext now runs G, the re-encryption and the KDF. The unbounded correction index (kem-02-4, High) is a separate check and is not costed.
- **kem-02-8.** Replace the four SM3-256 calls by one hash with 1024-bit output and an internal state at least as wide as the level, applied to `(ID(pk), m)` as §1.4 defines G. The report names this replacement, and the specification says that its SM3 plug-ins "will need to be replaced" for the 512-bit level. Scope: Sub-algorithm, specification and code. In the code the change is confined to the two loops at `ccakem.c:40-45` and `66-71`, and the package already declares the contest's 1024-bit `pseudohash` (`symmetric/auxfunc.h:35`). In the specification, the statement that SM3 instantiates Hash must name the 1024-bit construction. Impact: no transmitted object changes, because `m` is already 512 bits at every level. By calls and bytes, one call on 129 bytes replaces four calls on the same 129 bytes, which is no increase. If the replacement is the contest's `pseudohash` as coded, 27 SM3 compressions replace 12, which is +3.5% of the SM3 compressions of one encapsulation at Amoeba-1728 and +2.6% at Amoeba-2304 (estimate: the stand-in is assumed and the `Parse` count is an expectation); decapsulation hashes the same amount. Key generation does not call G. Only Amoeba-1728 and Amoeba-2304 are affected; the 384-bit set is optional and could be withdrawn, but the 512-bit set needs the repair. The same change applied to all five sets would be +6.9% at Amoeba-576 by the same count. Not relied on: moving the counter in front of `m` in the four SM3 calls. Neither the report nor the submitters propose it, and it keeps four 256-bit chains where the specification asks for a 1024-bit hash. Not checked: how a named 1024-bit hash would perform; the count treats the contest helper as the stand-in.
