No: widening the AXIS-1024 state from 1536 to 2048 bits repairs hash-02-3 and hash-02-4 together, and with eight 256-bit registers it adds an estimated 4% to 6% to AXIS-1024 hashing, while AXIS-512 and AXIS-768 do not change.

Impact: hashing +4% to +6% at AXIS-1024 (estimate)
Scope: Parameter set (large), specification and code
Assessed: 2026-11-24

## Attacks considered

- hash-02-3: The invertible AXIS state caps AXIS-1024 second-preimage security at 768 bits (Design, Confirmed)
- hash-02-4: Digest alignment gives a below-target AXIS-1024 preimage route (Design, Probable)

## Remediation

- **hash-02-3, hash-02-4.** The root cause of hash-02-3 is that every beat is an invertible map of a 1536-bit state, so a meet-in-the-middle costs 2^(1536/2) = 2^768 whatever the message rate. The route of hash-02-4 ends in the same meet-in-the-middle. The costed repair is the standard one for a narrow state: give AXIS-1024 a state of at least 2 × 1024 = 2048 bits. The meet-in-the-middle then costs 2^1024, and the route of hash-02-4, which is its digest-state search plus that meet-in-the-middle, is no longer below 2^1024 under the finding's own model. One change repairs both findings and is counted once. The cheapest form keeps eight registers and widens each from 192 to 256 bits: 8 × 256 = 2048, and §4 (physical p. 19) says that the design supports register sizes from 32 to 256 bits. Scope: Parameter set, specification and code. The algorithms stay: `UpRes`, `UpFull`, `ReUpFull` and `GenDigest` (physical pp. 8–9) and Algorithm 1 (physical p. 12) take ExL and UpL as inputs, and the beat structure, the S-box and the number of registers are unchanged. What changes is the parameter set of AXIS-1024: the register length, the tap arrays ExL and UpL, the constants of Table 1, and the single-register collision analysis of §3.2, which §4 calls the criterion for parameter selection; all are written for 192 bits and must be redone. AXIS-1024 would then no longer share `axis_core.c` and `def.h` with the other two instances. Impact: hashing +4% to +6% at AXIS-1024 (estimate). A beat is eight register updates. Each reads 13 state bits, XORs 6 and rotates the register by one position, and none of these counts depends on the register length, so a bit-serial count does not change. The portable code advances 32 beats at a time, and there the register shift and the state copy grow with the 64-bit words per register, from 3 to 4. A count of word operations in the reference block step gives +3.7%, or +5.8% when the copy and store of the state words are also counted. Blank beats and digest beats use the same step, so short messages change by the same percentage. The state grows from 192 to 256 bytes. AXIS-768 is exactly at its bound (1536/2 = 768), AXIS-512 is above it, and neither changes. The estimate has no margin, and its upper end lies in the 5% to 10% band, so the answer is by judgment: 8 × 256 bits puts the meet-in-the-middle exactly at 2^1024, and 256 bits is the largest register that §4 names. The register width is a costing aid, not a proposed parameter. A ninth register adds 12.5% more register updates per beat and would take the answer to Yes. So would more taps per register, or more blank beats: NFinBeat scaled by 256/192 adds about 16% to the shortest message. The report records no proposed fix. Not checked: whether taps exist for a 256-bit register that keep the collision argument of §3.2 at one message bit per beat and NFinBeat = 1024; how many digest bits the alignment of hash-02-4 fixes in a wider register; the AVX2 path. The report's witnesses compile the submitted code and were not run. Nothing was implemented or measured.

## Evidence

- Baseline: the state is 1536 = 192 × 8 bits (§1.1, physical p. 4; §2.1, physical p. 6). AXIS-1024 takes one message bit per beat, with NMeBeat = len(padded M), NFinBeat = 1024 and NDigGen = 1024 (physical pp. 5, 10–11). Table 2 (physical p. 12) claims 1024-bit preimage and second-preimage security for AXIS-1024. A hash candidate has no bandwidth. The reference timings of Table 9 (physical p. 24) were not used; the counts below are the whole evidence.
- State width: a meet-in-the-middle on an invertible s-bit state costs 2^(s/2), which is 2^768 at s = 1536 (hash-02-3). 2^(s/2) ≥ 2^1024 needs s ≥ 2048 = 8 × 256.
- hash-02-4 at s = 2048: the report's 2^891 to 2^892 digest-state trials, counted for the submitted registers, plus a 2^1024 meet-in-the-middle, is at least 2^1024.
- Work per beat, specification: `UpRes` (physical pp. 8–9) reads 6 bits of register j, 6 bits of registers j+1, j+3 and j+5 and one bit of register j−1, XORs 6 bits of register j, and rotates it by one position. `UpFull` applies it to the 8 registers.
- Work per block, reference source `hash-02/AXIS/Implementations/Reference_Implementation/AXIS-1024/axis_core.c` (`axis_core.c` and `def.h` are identical in the three instance directories, checked with `md5sum`): the byte-aligned AXIS-1024 path (`:1463-1544`) absorbs 4 message bytes per block step. The step is `axis_soa_step_default_block32` (`:533-541`, through the macro at `:1299`), which calls `axis_soa_step_default_block32_register_seqs` (`:544-562`). For each register the call makes 19 tap extractions (`:323-328`, `:434-452`, `:455-463`, `:466-483`), which are 33.5 word operations on average because an extraction that crosses a word takes three (`:240-266`); 6 ANDs and 13 XORs; and `axis_soa_compose_tape32` (`:486-503`), 28 operations, of which 10 shift the three 64-bit words of the register (`AXIS_REGISTER_WORDS` is 3, `def.h:8`) and 18 inject the two tapes. That is 80.5 operations per register and 644 per block.
- Calculation: a fourth 64-bit word adds two shifts and an OR to each register shift, 83.5/80.5 = 1.037. With the copy of the source state (`:545`) and the store counted as 3 + 3 word moves per register, growing to 4 + 4, the ratio is 91.5/86.5 = 1.058.
- Tipping cases: 9 registers instead of 8 is 9/8 = +12.5% register updates per beat. The shortest padded message has 128 bits and takes 128 + 1024 + 1024 = 2176 beats; with 1024 × 256/192 = 1365 blank beats it takes 2517, +15.7%.
