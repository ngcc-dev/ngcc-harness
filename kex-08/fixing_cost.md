## Attacks considered

- kex-08-1: The raw shared j-invariant is distinguishable from a uniform key (Design, Confirmed)
- kex-08-2: NIIKE-lv512 key generation cycles between two hard-coded secret keys (Implementation, Confirmed)

## Remediation

- **kex-08-1.** The root cause is that `NIIKE.KeyAgr` (Algorithm 5, physical p. 24), `NIIKE.ModifiedKeyAgr` for NGCC-III (Algorithm 9, physical p. 36) and `kex_derive_ss_a`/`_b` (`ngccapi/KEX_AlgorithmInstance.c:143–144, 158–159`) return the encoded j-invariant itself. The costed repair is the recorded proposal: apply a KDF to the shared key material. That is one added step at the end of Algorithms 5 and 9 and one hash call after `fp2_encode`. The proof of Theorem 9.1.7 (physical p. 56) already speaks of the digest H(K). Scope: Function, specification and code. Impact: none. NIIKE sends no protocol message, and the public key is not touched. The shared secret becomes the KDF output in place of the 62/128/2049-byte value of Table 7.1; it is not transmitted. The call asks for an output of at least 128/256/512 bits, which is shorter than the hashed value at every level. The added work is one hash over the encoded j-invariant (64/128/4100 bytes in the submitted code) per key agreement, against B = 35/70/1 class-group actions on r = 13/14/2 tuples. The proposal is quoted as reported and was not evaluated, and the updated implementation that the team announced was not seen. The specification names no hash (the proof uses a random oracle H), so the hash is costed by its input length alone.
- **kex-08-2.** The root cause is that the lv512 `make_SecretKey` ignores its DRNG argument and copies one of two literal vectors (`NIIKE-lv512/protocols/bundleprotocols_internal.c:53–70`). The sampling loop used at the other levels is present but commented out (`:71–78`). The specification is sound: NGCC-III uses `NIIKE.ModifiedKeyGen`, and Algorithm 8 line 1 (physical p. 35) samples each sk_i uniformly in [0, e_i], which is the range [0, B·e_i] of Algorithm 4 line 1 (physical p. 23) at B = 1. The repair is to make the code follow it by restoring that loop. Scope: Function, code; the optimized helper is the same file. Impact: none. No size depends on how the key is chosen. The submitted code skips no specified work that matters for speed. Both literal vectors lie inside the specified ranges, so they are valid samples, and the work of the class-group action does not depend on the key: Algorithm 7 (physical p. 35) and the shared `protocols/bundleprotocols.c:47–59` compute one ℓ_i-isogeny for every step t = 1, …, e_i, and the key only sets the swap bit. The restored loop makes about 1012 DRNG draws per key. Not checked: lv512 was not run, and its other differences from the specification (759 primes, key and shared-secret lengths) are outside this finding.
