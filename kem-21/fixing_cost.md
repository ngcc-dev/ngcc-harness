## Attacks considered

- kem-21-1: Viper-384 and -512 restrict the secret to a 256-bit seed (Implementation, Confirmed)
- kem-21-2: Viper-384 and -512 derive the encapsulation secret from a 256-bit seed (Design, Confirmed)

## Remediation

- **kem-21-1.** Root cause: key generation draws a 32-byte `sseed` (`kem.c:21,23`) and expands it into the whole secret vector s (`viper.c:501`). Algorithm 3 (physical p. 8) samples s from the full distribution, and §8.6 (physical p. 25) says only that a seed is expanded, without a length. The costed repair draws a seed of the profile length, 48 or 64 bytes, and has the sampler absorb all of it. It is the cheapest credible repair: widening a secret seed is the standard repair, and nothing transmitted depends on its length. Scope: Function, specification and code: the `sseed` buffer, the sampler's seed parameter and its two absorb lengths (`viper.c:421,425,437`), and the seed length, which §8.6 leaves out. Impact: none. The seed is not stored. The secret key holds s in expanded form (§3.2, physical p. 11), so no object changes size. Key generation makes the same XOF calls with the same output bytes, and the sampler call absorbs 16 or 32 more bytes.
- **kem-21-2.** Root cause: Algorithm 4 (physical p. 8) fixes the coins at 512 bits and σ at 256 bits for every profile, and r is derived from σ alone. The code already derives a σ of 48 or 64 bytes (`kem.c:32,39–41`), but the shared sampler reads 32 of them (`viper.c:517,569`). The costed repair makes σ as long as the profile target in Algorithm 4 and has the sampler absorb all of it, which is the same sampler change as for kem-21-1. The plaintext is already wide enough: m and K are 384 and 512 bits (Table 4, physical p. 11; `viper_params.h:73–75,87–89`), so only the coin width limits the session. Scope: Function, specification and code: the coin widths in Algorithm 4 and the sampler's absorb length. Impact: none. σ is never transmitted. The ciphertext carries µ, which is public and stays at 32 bytes, so the ciphertext does not grow. G already returns 2|K| bytes in the code, so no hash output grows. Encapsulation and decapsulation make the same XOF calls with the same output bytes. For both findings the XOF is the contest's `pseudoXOF` behind the names `shake128` and `shake256` (`viper_api_hash.c:6–21`), which the ruleset costs as an ideal replacement by calls and bytes. Counted that way, each operation makes one sampler call: key generation for s, and encapsulation and decapsulation, which re-encrypts, for r. That call absorbs 16 or 32 more bytes, and nothing else changes. With the input absorbed once and output in blocks of b bytes, the sampler call takes 36 blocks at b = 64 as submitted, 36 at Viper-384 and 37 at Viper-512 repaired, against 612 blocks of XOF work in key generation at Viper-512 and more in encapsulation and decapsulation, which add the dithers: at most +0.2% of the XOF work of any operation, and +0.0% at b = 136. The XOF work is only part of each operation, so the whole-operation change is smaller still. Alternative, not costed: in the helper as built, the longer seed takes two SM3 compressions per 32-byte output block where the submitted one takes one. That affects the sampler call only, which produces 7.9% of the XOF output bytes of key generation at Viper-384 and 6.3% at Viper-512 (7.7% and 6.2% in encapsulation), so even counted that way each operation grows by less than 8%. The same bound holds if the sampler ran on a sponge of capacity 2λ instead, where the rate ratio is at most 136/72 = 1.9. Not checked: the optimized trees beyond the lines that the report cites, and the native backends of Appendix D.
