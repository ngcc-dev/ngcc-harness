Yes: the repair of hash-05-2 gives every compression call a chunk counter, which takes 55 to 64 key bits from each message chunk and slows long-message hashing by 7.7% to 9.1% at uHash-512, 12.3% to 14.3% at uHash-768 and 28.6% to 33.3% at uHash-1024, while the repairs of hash-05-3 and hash-05-6 add no work.

Impact: long-message hashing +28.6% to +33.3% at uHash-1024 (count)
Scope: Function (small), specification and code
Assessed: 2026-11-23

## Attacks considered

- hash-05-2: Narrow-pipe iteration limits uHash second-preimage security for long messages (Design, Confirmed)
- hash-05-3: Unused partial-byte bits cancel padding and give trivial collisions (Implementation, Confirmed)
- hash-05-6: 32-bit length arithmetic gives collisions between 4 GiB messages (Implementation, Confirmed)

## Remediation

- **hash-05-2.** The root cause is an h-bit chaining value with no chunk index in any compression call and no length in the padding, so a prefix that reaches any of the l chaining values of a long target can be continued with the target's own chunks. The costed repair is the standard block counter: the chunk index i becomes an input of every compression call, which ties a trial prefix to the one chaining value at its own position. In uHash every input bit of the cipher is in use. The plaintext is u^1 ⊕ (j − 1), and the 4n-bit key holds (b − 1)n chaining bits and (5 − b)n message bits (§2.1, physical p. 9). A counter with bits of its own therefore takes key bits from the message chunk. With a 64-bit counter the chunk carries 704, 448 and 192 message bits instead of 768, 512 and 256, and a chunk still costs b cipher calls. The narrowest counters that number every chunk of a message of 2^64 − 1 bits have 55, 56 and 57 bits and leave 713, 456 and 199 message bits. Scope: Function, specification and code: the key formation in Algorithm 1 (lines 7 and 12), the chunk length in padding and splitting (§1.2.1, §1.2.2), and the same steps in `Padding` and the three hash routines. Impact: long-message hashing +7.7% to +9.1% at uHash-512, +12.3% to +14.3% at uHash-768 and +28.6% to +33.3% at uHash-1024 (count). The lower figures are for the narrowest counters, which are the cheapest form of the repair, and the upper figures are for a 64-bit counter. uHash-768 and uHash-1024 stay above 10% at any counter width. The widths are costing aids, not proposed parameters. Short messages: a one-chunk message keeps its b cipher calls, and only lengths within the counter width of the chunk size need one more chunk, which counts as none. Alternatives that are not the costed repair: a counter that is only XORed into the key or the plaintext lands on bits that the message or the chaining value already fills. The report records for the final iteration that such a counter in the key cancels against message bytes (hash-05-4), and no standard construction or proposal for the plaintext position was found, so a free counter is not assumed. A counter XORed onto the chaining input is also the form whose weakness was shown for Streebog (Guo, Jean, Leurent, Peyrin and Wang, "The Usage of Counter Revisited", SAC 2014). If a counter that takes no message bits were accepted as a repair, the impact would be none and the answer No. Appending the message length to the padding leaves the chaining value h bits wide and unindexed, which is the stated root cause. Widening the chaining value by one branch costs more: uHash-512 with b = 3 and a = 2 runs at 2.25 times the cipher calls per message block, uHash-768 with b = 4 and a = 1 at 2.67 times, and at uHash-1024 a fifth branch leaves no key bits for the message. The report records no proposed fix. Not checked: whether a counter that takes no message bits would remove the root cause; the AVX2 code, where the branches share registers. The report's witnesses run the submitted libraries and were not run. Nothing was implemented or measured.
- **hash-05-3.** Mask the unused bits of the last partial byte before the pad bit is set, as the report's remediation text gives it. Scope: Single line, code. It is one statement: `CryptHash_AlgorithmInstance.c:463` in the reference source, and `:6199`, `:6256`, `:6394` and `:6560` in the optimized source, where the three hash routines pad inline. The specification pads the bit string as M ∥ 1 ∥ 0* (§1.2.1) and stays as it is. Impact: none. The padded length and the number of chunks do not change.
- **hash-05-6.** Compute the padded length, the byte counts and the chunk count in 64-bit arithmetic. Scope: Function, code: the `(int)` casts in `Padding` and in `uHash512`, `uHash768` and `uHash1024` (reference `:450-453,492-494,512,652-654,675,847-849,874`; optimized `:6242-6245,6267,6378-6383,6400,6545-6548,6571`), the `int` loop counters over the padded length in the reference source (`:496,656,851`), and the `int` chunk index and its offset product in the optimized source (`:6234,6278`, `:6370,6415`, `:6536,6586`). The specification already allows messages of up to 2^64 − 1 bits (physical p. 3). Impact: none. Below the wrapping lengths the code already runs all l chunks with b cipher calls each, so no specified work was skipped there, and the repair adds none. Not checked: the reference routines hold the whole padded message in one allocation (`:495,655,850`), which limits the reachable length in practice and is outside this costing.
