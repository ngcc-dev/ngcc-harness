Impact: not bounded
Scope: Construction (large), specification and code
Assessed: 2026-11-24

## Attacks considered

- kex-06-1: MAMBA-NIKE-384 and -512 use only 256 secret-seed bits (Implementation, Confirmed)
- kex-06-2: Static-key reconciliation allows active key recovery (Design, Confirmed)

## Remediation

- **kex-06-1.** The root cause is that the static secret `s`, the ephemeral secret `r` and the HelpRec bits of MAMBA-NIKE-384 and -512 are expanded from one 32-byte `noiseseed` (`nike.c:195–208, 230–261`) by ChaCha20 (`poly.c:115–127`, `error_correction.c:74`). §8.5 and §8.6 (physical pp. 22–23) specify this seed length and expander for every profile, while Algorithms 1 and 2 (physical p. 8) sample from the full distribution. The costed repair is the usual one: a seed of at least 48 bytes at -384 and 64 bytes at -512, and an expander that takes it. ChaCha20 has a 256-bit key, so the expander is replaced. SHAKE256, which the submission uses as its KDF, has a 512-bit capacity and so only 256-bit generic security, which does not carry the 384- or 512-bit level. The costed expander is a Keccak-f[1600] sponge with capacity 2λ: 768 bits at -384 and 1024 bits at -512, a rate of 104 and 72 bytes. Scope: Sub-algorithm, specification and code. Impact on sizes: none. The noise seed is never sent, |pk| and |M1| hold only the public seeds ρ and µ (§3.2), and the API secret key stores the polynomial and not the seed. Impact on speed: key generation at most +1.6% at -384 and +5.5% at -512, Pass1 at most +0.9% and +2.9%, Derive unchanged (estimate, upper bounds; the ChaCha20 work that is removed is not subtracted). These figures are for the portable reference code. They take a Keccak permutation in the reference build to cost no more than the bound that the optimized build's timings give, which was not checked. For the AVX2 code the same bound is loose: it allows up to +34% for key generation and +18% for Pass1 at -512. The share of hashing in that code was not determined. With SHAKE256 instead, which does not meet the level, the bounds would be +1.2% and +2.9% for key generation. The 128-, 192- and 256-bit sets are not affected. Drawing the centered-binomial bits directly from the random source, as Algorithm 1 line 3 reads, is an alternative whose cost depends on that source.
- **kex-06-2.** The root cause is that the static responder runs D4 reconciliation on an unauthenticated, attacker-chosen `M1` under its long-term secret and releases a key derived from the result (Algorithm 3, physical p. 9; `KEX_AlgorithmInstance.c:336–366`). The report records no proposed fix. No Single line or Function repair meets the conditions. Rejecting the monomial probe messages would only block the witness. The recovery needs 213 to 666 session-key reveals, so no key-use limit of 2^64 or more removes it, and limiting a static key to one use is not a repair. Authenticating the initiator does not exclude a registered attacker. The standard defence of a static key against chosen messages is a re-encryption check, in which the responder recomputes the received message from recovered randomness. A reconciliation transcript carries no such randomness, and §B.4 (physical p. 29) itself says that the PKE/KEM route does not fit this message. The core mechanism therefore has to change, with a new security proof. Scope: Construction, specification and code. Impact: not bounded, because no costed proposal exists. As an indication only, and not a costed repair: a re-encryption check would have Derive recompute the initiator's two ring products besides its own, three where the submission has one, and such a check is normally paired with a failure probability far below the submitted 2^-37.81 to 2^-42.44 (Table 3), which would move the parameters and sizes as well. Neither effect was estimated. Xiong and Wang's paper was not read for a proposed fix.

## Evidence

- Baseline sizes: Table 4 (physical p. 10) gives |pk| = 1184/1312/1312/2848/2848 and |M1| = 1568/1568/1568/3360/3360 bytes for the 128/192/256/384/512 sets.
- Control: §3.2 (physical p. 10) gives |pk| = 32 + n·t_pk/8 and |M1| = 32 + n·t_u/8 + n/4. With Table 3 (physical p. 9): 32 + 1024·9/8 = 1184, 32 + 1024·10/8 = 1312, 32 + 2048·11/8 = 2848; 32 + 1280 + 256 = 1568, 32 + 2816 + 512 = 3360. Neither formula contains the noise seed, so the values after the kex-06-1 repair are the same.
- Secret stream: `poly.c:117` sets NOISE_BYTES = n·2η/8, which is 1024 bytes at -384 (η = 2) and 2560 bytes at -512 (η = 5); HelpRec draws n/32 = 64 bytes. ChaCha20 today: 16 and 40 blocks of 64 bytes, plus 1. Keccak-f[1600] at capacity 2λ: ⌈1024/104⌉ = 10 permutations at -384 and ⌈2560/72⌉ = 36 at -512, plus 1 for HelpRec in Pass1. For comparison, SHAKE256 at 136 bytes: ⌈1024/136⌉ = 8 and ⌈2560/136⌉ = 19, plus 1.
- Permutations already run at n = 2048: `poly_uniform` 20 (13 bits per coefficient, 168-byte blocks; `poly.c:43–75`), each dither 25 (2 bytes per coefficient, 84 coefficients per block; `nike.c:108–133`), the KDF 47 (16 + 64 + 2848 + 3360 = 6288 bytes at 136; `nike.c:165–185`). KeyGen runs 45 and one ring product, Pass1 142 and two, Derive 97 and one (`nike.c:211, 253, 256, 306`).
- Bound on one permutation: `fips202.c` is byte-identical in the reference and optimized trees, and Derive runs 97 permutations in both, so in the optimized build one costs at most 322/97 = 3.32 kCy (-384) and 317/97 = 3.27 kCy (-512) of the Derive times in Table 7 (physical p. 12). The reference build compiles the same file without `-mavx2 -march=native` (Table 5, physical p. 11), and the bound is applied to it unchanged. Against the reference times of Table 6 (physical p. 12): KeyGen 10 × 3.32/2140 = +1.6% and 36 × 3.27/2139 = +5.5%; Pass1 11 × 3.32/4219 = +0.9% and 37 × 3.27/4212 = +2.9%. With SHAKE256: KeyGen 8 × 3.32/2140 = +1.2% and 19 × 3.27/2139 = +2.9%. A reference permutation would have to cost 1.8 times the bound to bring KeyGen at -512 to 10%. Against the optimized times of Table 7 the bound gives 36 × 3.27/343 = +34% for KeyGen and 37 × 3.27/690 = +18% for Pass1 at -512. The timings are the specification's; nothing was measured here.
- For kex-06-2: Table 3 (physical p. 9) gives ρ_key = 2^-42.44, 2^-40.65, 2^-39.97, 2^-39.69 and 2^-37.81. Table 6 gives Derive 1005 to 2085 kCy and Pass1 2065 to 4219 kCy, consistent with one and two ring products.
