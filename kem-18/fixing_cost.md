## Remediation

- **kem-18-1.** Expand the comparison result to `0x00` or `0xff` before the select, as the report states. The code negates an arbitrary nonzero byte (`KEM_Loong.c:302`). Algorithm 24 replaces the whole key on mismatch, so the specification is sound. Scope: Single line, code, in the twelve `KEM_Loong.c` files. Impact: none.
- **kem-18-3.** The report records no proposed fix. The attack cancels the block-negacyclic term of `U′` and is left with k2·N·(N−1) public equations in the k2·N short coefficients of `r2`: 48, 96 and 160 unknowns. The repair costed keeps the algorithms and changes the parameter tables: raise k2 until that instance alone reaches the level. The specification already sets k2 by the cost of eliminating the unstructured components, but it counts brute force only; the repair counts lattice reduction there. With the specification's own primal condition applied to the equations, the smallest k2 is 43 at Loong128 (submitted 4), 59 at Loong256 (6) and 72 at Loong384 (8). Lowering k1 so that (k1 + k2)·N keeps its submitted value, as the failure formula takes that dimension as input, gives (k1, k2) = (9, 43), (11, 59) and (8, 72). In these three sets N is already the smallest value with N² ≥ λ, so it cannot be lowered to shrink the k2·N² term. Scope: Parameter set, specification and code (Table 2, the security analysis, and `K1`, `K2` and the length macros in `params.h`). Impact: public key +437%, +490% and +519% and ciphertext +426%, +452% and +501% at Loong128, Loong256 and Loong384. The public matrix expanded in every operation grows 8.0, 10.5 and 13.8 times and the multiplications of one encryption 7.9, 10.4 and 13.6 times; the three operations have nearly equal stated timings, so each grows by about that factor. With k1 kept at its submitted value the figures are larger (public key +477%, +522%, +546%). This is a lower bound. The model ignores the quotient projection that the Loong384 attack uses and the correlation between equations, both of which help the attacker, and the failure probability and the full security analysis were not redone. The quotient model of kem-18-2 (High, Lead, not costed) gives no finite cost at the lowered k1 for Loong128 and Loong384, where the ring rows supply 9 and 8 polynomial samples for 52 and 80 polynomial unknowns. The unstructured block becomes most of the dimension, which moves the candidate towards an unstructured LWE scheme; the specification's own comparison lists FrodoKEM-640 at 9,616 and 9,720 bytes. A change to the construction that stops the cancellation is not proposed anywhere and is not costed. Loong512 is not in the finding and is not costed.
- **kem-18-4.** Compute the rejection key over the received ciphertext, `H(salt‖c)`, as Algorithm 24 line 4 specifies and the report states. The code re-encrypts into the hashed buffer (`:289`) and hashes `salt‖c′` (`:295`). Scope: Function (`kem_dec`), code. Impact: none. The code already hashes `SEED_BYTES + CIPHERTEXT_BYTES` bytes once per call; the repair changes which ciphertext is in that buffer. The re-encryption then needs its own buffer, 1,512 to 10,848 bytes of stack.
